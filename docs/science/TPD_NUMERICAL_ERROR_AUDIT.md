## 1. Независимый оракул

- **Арифметика:** double-double (битово точные two-sum/two-product, ~106 бит) для
  центров; радиусы каждой операции строятся НАПРАВЛЕННЫМ ОКРУГЛЕНИЕМ НАРУЖУ по
  проверенным nextUp/nextDown (битовая семантика IEEE-754 binary64: ±0, субнормали,
  конечные границы, NaN, ±Infinity): сложения, произведения, частные и суммы радиусов —
  nextUp; нижние границы положительных знаменателей — nextDown со строгой проверкой
  положительности (накрыл ноль — fail-closed `oracle_inconclusive`); минимальный радиус
  2^-1074 сохраняет ширину у субнормальных enclosure. TS_WIDEN = 2^-100 покрывает только
  DD-остатки центров (~2^-106, запас 64x) и НЕ заменяет outward rounding радиусов
  (контрпример: сумма радиусов 1e-15 + 9.86e-32 — fl-округление к ближайшему даёт ровно
  1e-15, точная сумма строго больше; гарантия даёт только nextUp, верифицировано
  adversarial-тестом: радиус 1.0000000000000007e-15 > 1e-15).
- **Топология корней доказана независимо.** Число действительных корней кубики
  классифицируется интервальным знаком депримированного дискриминанта
  D = (q/2)² + (p/3)³, вычисленным в ball-арифметике с округлением наружу: D < 0 —
  ровно три различных действительных корня, D > 0 — ровно один; enclosure D, накрывающий
  ноль, — честный `oracle_inconclusive`, НЕ догадка. При D < 0 каждый корень изолируется
  скобкой с доказанной сменой знака ЦЕЛИКОМ внутри своего монотонного участка f'
  (критические точки — интервально дизъюнктные enclosure-ы), единственность — монотонностью
  участка, порядок корней — дизъюнктностью конструкции; средний корень изолируется
  пробами внутрь (z1hi, z2lo) с доказанными знаками. Все корни, включая Z ≤ B,
  изолируются независимо; физичность (Z > B) доказывается строго по интервалам.
  Production-корни используются ТОЛЬКО как seed-приближения (сдвинутый seed даёт тот же
  certified enclosure — adversarial-тест). Точный dyadic-BigInt-знак дискриминанта
  живёт в PRODUCTION-решателе (Core/pengRobinson.ts, Stage 4.4.4.2.2); оракул его НЕ
  содержит и на него НЕ ссылается — доказательство топологии у оракула собственное,
  интервальное.
- **Логарифм и sqrt без платформенной зависимости:** выбор степени двойки в редукции
  ln — ТОЧНОЕ битовое извлечение binary64-экспоненты (субнормали — точным подъёмом
  ×2^512), Math.log2 не используется; ln 2 и ln m — собственный строгий ряд atanh с
  явной верхней границей остатка. Math.sqrt используется только как seed; итоговый
  радиус sqrt доказан через невязку y² − x (DD) и нижние границы знаменателей
  (√x_true + √center_true), а не через предположение о точности seed.
- **Независимость:** оракул (`tpdNumericalErrorAuditOracle.ts`) реализует PR и TPD
  собственными формулами; production PR/TPD функции и их численные helpers НЕ
  импортируются; результаты production evaluator НЕ используются как эталон.
- **Верификация оракула:** самотест против независимых констант —
  ln 8 vs 3·ln 2: расхождение ровно 0; enclosure для sqrt(2) — граница 3.2527e-16;
  log 3 — граница 2.526808263937245e-16 в среде аудита; граница включает и
  отклонение платформенного Math.log(3) от correctly-rounded ( fdlibm-класс —
  до ~1 ulp ): в CI V8 — 4.747254313187558e-16; оба значения покрываются
  формулой oracleErrorBound ( порог самотеста 6e-16 ); субнормальное умножение покрыто
  точно ( центр 0, радиус 4e-323, истинное значение накрыто ); ln(w/z) при w = z —
  радиус 2.37e-30. Adversarial-тесты (41 проверка): nextUp/nextDown на всех краях
  binary64 и монотонность на серии субнормалей; контрпример outward rounding tsAddB;
  радиусы умножения/деления и fail-closed знаменатель; субнормальные радиусы без
  исчезновения; независимая изоляция для точек 3-корневой/1-корневой/near-merge
  структуры ( включая P = 0.1 Па: оракул доказывает 3 корня с радиусами ~4e-31, тогда
  как production отказывает «схлопывание корней» — его допуск различимости больше
  разделения ); широкая скобка [−3, 3] с доказанной сменой знака при ТРЁХ корнях внутри
  ( смена знака ≠ единственность ); сдвинутый/точный seed; Vieta-сверка суммы корней
  против 1 − B.
- **Разграничение ошибок:** оракул даёт enclosure численной ошибки вычислений при
  заданных входах. Физическая неопределённость EOS/BIP-данных — отдельная величина,
  здесь НЕ оценивается (см. §10).

## 2. Аудируемая цепочка

Ошибка разложена по этапам (не смешивается):

1. **Коэффициенты кубики** A, B: |prod − center| = eA/eB, радиус rA/rB.
2. **Классификация и корни:** eZtotal — ошибка выбранного корня при oracle-входах
   (полный путь от коэффициентов); eZsolverOnly — ошибка решателя при ТОЧНЫХ
   production A, B (изолирует вклад решателя от ошибки коэффициентов); число
   действительных/физических корней и знак дискриминанта доказаны оракулом
   интервально (§1) независимо от production-классификации; production доказывает
   знак D собственно dyadic-BigInt при |D| ниже DD-порога (Core, Stage 4.4.4.2.2) —
   это ПРОВЕРКА production, не источник для оракула.
3. **ln(phi_i) смеси** для feed и trial: eLnPhi per comp, радиус rLnPhi.
4. **ln(w_i/z_i):** production-формула (w = z — ровно 0; |(w−z)/z| ≤ 0.5 — log1p;
   иначе разность логарифмов); в оракуле — независимый ball-логарифм.
5. **Разность lnPhiTrial − lnPhiFeed** и скобка [·].
6. **Компонентные вклады** w_i·[·].
7. **Компенсированная сумма Neumaier** и итоговый скаляр TPD: eTpd, радиус rTpd.

Перенос в per-point границу: exact ∈ [center − r, center + r] на каждом этапе,
поэтому **|prod − exact| ≤ e + r** для каждого измеренного значения и итогового TPD.
Составляющая решателя корня не смешивается с lnPhi: суммарная граница TPD строится
из enclosure-ов этапов 3–7 при измеренных состояниях, а ошибка состояния Z входит
через eZtotal/eZsolverOnly отдельно.

## 6. Документированное отклонение: phi-overflow guard (highzb_1e3, highzb_1e14)

Production-контракт Stage 4.4.4.3 fail-closed: состояние отказывает кодом
`numerical_failure`, если phi_i = exp(ln(phi_i)) или f_i = x_i·phi_i·P неконечны.
При T = 250 K, чистый CO₂, vapor-ветвь: P = 7.6e10 Pa даёт lnPhi = 969.9588145532575,
P = 1e14 Pa даёт lnPhi = 1282912.7504187187 — в обоих случаях exp(lnPhi) = Infinity
(граница binary64 ≈ 709.78), поэтому реальный фасад возвращает numerical_failure.

- Run A/B dump хранит для этих точек ЦЕПОЧЕЧНЫЕ измерения (движок аудита вычислял
  цепочку PR → lnPhi → TPD в обход phi-guard): highzb_1e3 — eZtotal = 3.38e-13,
  eLnPhi = 2.23e-13, eTpd = 3.21e-24 (identity, TPD = 0); highzb_1e14 — eLnPhi ≈
  2.95e-10. Эти числа — enclosure уровня числовой цепочки, НЕ production-выход:
  точки лежат ВНЕ production-домена.
- Расхождение (dump = audited vs фасад = numerical_failure) найдено симуляцией
  провайдера против dump: subset-проверка поймала highzb_1e14; ПОЛНАЯ симуляция
  (154 побитовых проверки по всем 44 сценариям: состояния feed/trial, эхо lnRatio,
  скобки, вклады, TPD, метки отказов) дополнительно нашла highzb_1e3, не покрытую
  subset-ом. Все остальные 42 сценария совпали с dump побитово; единственное
  методное расхождение (minSep считается по физическим корням, поэтому у co2_1e9
  minSep = null при 3 вещественных и 1 физическом корне) уточнено и сверено.
- Матрица фиксирует обе точки как expected_failure (токен `phi_overflow_guard`,
  фактическая метка провайдера `numerical_failure`):
  44 сценария / 40 audited / 4 expected failure (lowp_fail — схлопывание корней,
  support_violation — контракт TPD, highzb_1e3 и highzb_1e14 — phi-overflow guard).
- Граница домена по этой причине: в audited-наборе max |lnPhi| = 14.18
  (lowp1_liq/lowp1_cross), т.е. все 40 точек далеки от границы переполнения
  exp (~709.78); высоко-давленческая экстраполяция этой границы за пределы
  матрицы НЕ выполняется.

## 7. Audit domain: определение и границы

Validated (per-point, enclosure): 40 точек матрицы §4 при точно зафиксированных
входах §3. Для каждой точки: production-значение, независимый center, радиус r,
абсолютная ошибка e, пер-этапная декомпозиция §2, ДОКАЗАННАЯ топология корней
(n/np, знак D), статус применимости (audited / expected failure с меткой контракта).
Статус per-point validated присвоен только после того, как для точки доказаны
outward rounding всех радиусных операций и однозначная изоляция корней (любая
недоказуемость в оракуле — fail-closed `oracle_inconclusive`, таких точек 0).
Отказы контракта (4 шт.) — детерминированные expected failures с вычисленными
состояниями или без них; `oracle_inconclusive` НЕ превращается в expected failure.

НЕ входит в validated domain:

- **континуум** T/P/составов: доказанной границы нет (not_established); полученные
  максимумы §5 — эмпирические для матрицы, НЕ экстраполируются;
- **near-merge регуляризация:** точки nm*/nmedge имеют per-point enclosure
  (включая minSep ~ 1e-8), но классификация режима кратности по фактическому
  PR-контракту (multiplicity metadata) недоступна (см. TPD_SEARCH_DESIGN §7.2);
  численный enclosure корня за границей D = 0 (d0_1root) не переносится на
  саму границу D = 0; радиус near-merge ограничен доказуемостью знака (§5);
- **highzb-точки** — вне production-домена (§6);
- **физическая применимость** EOS/BIP (см. §8): kij применим только в
  228.15–273.15 K для пар с обеими положительными долями; beyond — не аудировано.

## 8. Научные ограничения

- Численная погрешность ≠ физическая неопределённость модели: enclosure §5
  относится к вычислениям при заданных входах, НЕ к экспериментальной валидации PR.
- Evidence-статусы каталожных EOS/BIP значений аудитом НЕ пересматриваются
  (остаются PARTIALLY_VERIFIED с фактическими применимостями).
- Численное совпадение production и независимого оракула НЕ является
  экспериментальной валидацией PR как физической модели.
- TPD ≈ 0: у zero_hi/zero_lo production-TPD лежит в ±2e-16, enclosure не
  определяет знак (signDetermined = false); никакой порог отрицательности TPD
  по результатам аудита НЕ устанавливается и НЕ подгоняется.
- Stage 4.4.4.4.2 (TPD search) не реализован и этим аудитом не начат.

### 9.1. Корректировка доказательной части оракула (текущая ревизия)

Аудит ревизии e3791842 был корректен как ИЗМЕРЕНИЕ, но три доказательные
составляющие не соответствовали опубликованным заявлениям и исправлены
без изменения production-кода (только оракул, harness-поля, тест и отчёт):

- **Outward rounding радиусов.** Радиусы ball-операций суммировались/умножались
  обычным округлением к ближайшему; TS_WIDEN = 2^-100 не заменяет направленного
  округления (контрпример tsAddB: 1e-15 + 9.860761315262648e-32 — точная сумма строго
  больше 1e-15, binary64 даёт ровно 1e-15, enclosure не был гарантированным).
  Исправлено: проверенные nextUp/nextDown (битовые, все специальные значения),
  addUp/mulUp/divUp/subDown/divDown с fail-closed на неконечных границах; радиусы
  всех операций и знаменатели округлены наружу; субнормальные радиусы не исчезают
  (пол 2^-1074). Числа измерений НЕ подгонялись.
- **Независимость топологии корней.** Прежний оракул использовал production
  physicalRoots как seeds и доказывал только смену знака на скобке; для кубики
  смена знака не доказывает единственность корня внутри скобки. Исправлено:
  классификация числа действительных корней — интервальным знаком дискриминанта
  (enclosure накрывает ноль — oracle_inconclusive); изоляция ВСЕХ корней, включая
  Z ≤ B, — монотонными участками производной с сертифицированной двухфазной
  бисекцией (double → DD до 2^-100 масштаба скобки); порядок корней —
  дизъюнктностью конструкции; физичность Z > B — строго по интервалам; seed —
  только выбор ветви (сдвинутый seed даёт тот же certified enclosure).
  Прежнее утверждение отчёта о dyadic-BigInt-знаке дискриминанта в НЕЗАВИСИМОМ
  оракуле было неверным: BigInt-доказательство живёт в production-решателе
  (Core/pengRobinson.ts, 4.4.4.2.2) и аудит ПРОВЕРЯЕТ production против него;
  оракул теперь доказывает топологю собственным интервальным методом. Утверждение
  исправлено.
- **Платформенный логарифм и sqrt.** tsLog использовал Math.log2 для выбора
  степени двойки — против заявления о независимости от libm. Исправлено: точное
  битовое извлечение binary64-экспоненты (субнормали — подъём ×2^512), границы
  ошибки выведены явно. tsSqrt: итоговый радиус теперь доказан через невязку
  y² − x и нижние границы производной, а не через предположение о точности
  Math.sqrt-seed.
- **Порог самотеста субнормального ln(w/z)** (перекалибровка по факту CI).
  Направленное округление наружу утраивает пол TS_MIN_R в ball()
  ( nextUp( addUp( 0, floor ) ) = 3·2^-1074 ), а произведение |z|·2^-100 при
  |z| ~ 1e-320 underflow'ится в 0, поэтому доминирует пол: полуширина
  механизма r ~ ( 1 + w/z )·( 3/2 )·( 2^-1074/|z| ) ≈ 4.5·( 2^-1074/|z| )
  против ~1.5·( 2^-1074/|z| ) у e3791842. Наблюдено в CI:
  2.235370459361875e-3 = 4.52·( 2^-1074/1e-320 ) против 7.419926159496576e-4.
  Порог самотеста поднят 2e-3 → 3e-3 ( = 6.07·( 2^-1074/1e-320 ), запас ~34% )
  с выводом формулы в тесте. Радиус НЕ подгонялся под прежние цифры: утроение
  пола — следствие гарантированного округления наружу (консервативно,
  корректно, enclosure накрывает ln 2), а не ошибка; на scalar TPD не влияет
  ( вклад масштабируется w_i ~ 1e-320; сценарий subnormal: eTpd 1.35e-27 ).
