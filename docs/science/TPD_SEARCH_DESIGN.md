## 0. Первичные ориентиры и принцип заимствования

Первичные ориентиры литературы:

1. **Michelsen (1982)**, *The Isothermal Flash Problem. Part I.
   Stability*, Fluid Phase Equilibria 9(1), 1–19, DOI
   `10.1016/0378-3812(82)85001-2`; публичная копия PDF:
   `https://www.ipt.ntnu.no/~curtis/courses/PhD-PVT/Extra-Papers/fpe-flash-stability.pdf`
   — исходная формулировка TPD, стационарное условие, ненормированные
   (псевдомольные) переменные и вспомогательная функция, successive
   substitution, инициализация по Wilson K-values.
2. **Baker, Luks, Michelsen (1982)** — критерий касательной плоскости
   (tangent-plane criterion), на который опирается TPD-анализ
   (Baker–Michelsen-критерий).
3. **GEOS documentation**, раздел Stability analysis (Compositional
   Multiphase Fluid Model,
   `https://geosx-geosx.readthedocs-hosted.com/en/latest/coreComponents/constitutive/docs/CompositionalMultiphaseFluid.html`)
   — пример промышленной реализации: инициализация двух пробных
   смесей по Wilson K-values — в терминологии GEOS «lighter trial
   mixture» y_i = z_i/K_i и «heavier trial mixture» y_i = z_i·K_i, —
   решение стационарного условия successive substitution, переход к
   negative two-phase flash при обнаруженной неустойчивости.
   Словесные метки lighter/heavier — СОБСТВЕННАЯ номенклатура GEOS,
   и словесные метки фаз НЕ переносятся в наш API: идентификаторы
   стартов нейтральны и описывают только формулу (§2.1). GEOS
   решает ПОЛНЫЙ flash; наш этап 4.4.4.4.2 этого НЕ делает.
4. **Three-Phase Equilibrium Calculations of Water/Hydrocarbon/
   Nonhydrocarbon Systems Based on the EOS in Thermal Processes**
   (PMC8696998) — свидетельство чувствительности stability analysis к
   выбору начальных K-values в трёхфазных водо-углеводородных
   системах: выбор начальных приближений влияет на результат анализа
   устойчивости и должен быть обоснован отдельно.
5. **A Line-Search-Based Algorithm for Multiphase Flash Calculations
   with CO2–Hydrocarbon System**, ACS Omega 9(32), 34370 (2024),
   PMC11325433 — современное peer-reviewed описание двустороннего
   уравнения Michelsen: жидкоподобный feed → пароподобная пробная
   фаза Y_i = z_i·K_i^Wilson; пароподобный feed → жидкоподобная
   пробная фаза Y_i = z_i/K_i^Wilson (основа конвенции направлений
   в §2.1); там же: вспомогательная TPD-функция в псевдомольных
   переменных Y имеет те же стационарные точки и те же знаки
   стационарных значений, что исходная TPD.
6. Расширения инициализации в литературе (например, улучшенная
   двусторонняя tangent-plane инициализация Ivanov & Stateva,
   Ind. Eng. Chem. Res., DOI `10.1021/ie061361b`) — ориентир для
   СТРУКТУРЫ набора стартовых точек, НЕ источник числовых порогов.

**Принцип заимствования**: алгоритмические ИДЕИ (Wilson starts,
successive substitution, двусторонняя инициализация) применимы к
любому EOS-моделированию пробной фазы и переносятся на наш PR-код
(4.4.4.3) с адаптацией к его контрактам. Числовые ПОРОГИ из внешних
реализаций НЕ копируются автоматически: каждый порог ниже выведен из
точности НАШЕГО TPD-evaluator (4.4.4.4.1) и масштаба суммируемых
вкладов, а неопределённые величины явно помечаются как
предварительные (§6.5). Распространённый порог −1e−8 НЕ принимается
по умолчанию.

## 1. Математический контракт

### 1.1. Исходная TPD-функция

Исходная TPD-функция (обозначение Michelsen):

```
g(w; z) = SUM_{i: w_i > 0} w_i [ ln w_i + lnPhi_i(w) − h_i ],
h_i = ln z_i + lnPhi_i(z)
```

через h_i она эквивалентна формуле Stage 4.4.4.4.1:
w_i [ln(w_i/z_i) + lnPhi_i(w) − lnPhi_i(z)] — безразмерная dG/RT:
расстояние от касательной плоскости к поверхности энергии Гиббса
смеси в точке feed z. Значение и вклады вычисляет существующий
evaluator 4.4.4.4.1 (контракт НЕ меняется: скаляр + вклады,
компенсированная сумма Neumaier, устойчивый ln(w/z), fail-closed
коды). Поиск 4.4.4.4.2 — ОРКЕСТРАЦИЯ вокруг этого evaluator:
генерация пробных точек, пересчёт PR-состояний пробной фазы,
итерации к стационарным точкам, классификация.

### 1.2. Допустимое пространство составов

- носитель feed: supp(z) = { i : z_i > 0 };
- допустимый пробный состав: w_i >= 0, SUM w_i = 1 (в существующем
  допуске суммы состава, БЕЗ нормализации), и
  **supp(w) ⊆ supp(z)**: положительная trial-доля при z_i = 0
  запрещена — это уже структурный отказ `support_violation`
  контракта 4.4.4.4.1 (0·ln 0 не вычисляется, ln(w_i/z_i) при
  z_i = 0 не определён);
- никакой epsilon-подмены нулевых долей и никакой молчаливой
  нормализации состава: нарушенная сумма — отказ, а не исправление.

### 1.3. Стационарное условие и вспомогательная функция Michelsen

**Стационарное условие на нормированном составе.** Внутренняя
стационарная точка g по допустимым w (все активные w_i > 0 на
рассматриваемом носителе) удовлетворяет

```
ln w_i + lnPhi_i(w) − h_i = k   (для всех активных i)
```

где k — ОДНА И ТА ЖЕ константа для всех активных компонентов
(множитель Лагранжа ограничения нормировки). Для нормированного
состава значение функции в стационарной точке равно этой константе:

```
g_sp = SUM_i w_i [ln w_i + lnPhi_i(w) − h_i] = k · SUM_i w_i = k
```

**Ненормированные псевдомольные переменные Michelsen.** Вводятся
через константу стационарной точки:

```
Y_i = exp(−k) · w_i
```

Тогда стационарное условие принимает нулевую форму

```
ln Y_i + lnPhi_i(w) − h_i = 0   (для всех активных i)
```

а нормировка восстанавливается делением:

```
w_i = Y_i / SUM_j Y_j
```

**Вспомогательная функция Michelsen** (в терминах Y, при
w = Y/ΣY):

```
g*(Y) = 1 + SUM_i Y_i [ ln Y_i + lnPhi_i(w) − h_i − 1 ]
```

В стационарной точке нулю равна НЕ вся скобка: нулевую форму
стационарного условия даёт её часть ln Y_i + lnPhi_i(w) − h_i = 0,
а вся скобка [ ln Y_i + lnPhi_i(w) − h_i − 1 ] равна **−1**,
поэтому

```
g*_sp = 1 − SUM_i Y_i = 1 − exp(−k) = 1 − exp(−g_sp)
```

**Соответствие g* и g.** g* и g имеют соответствующие стационарные
точки (Y* ↔ w* = Y*/ΣY*) и ОДИНАКОВЫЙ ЗНАК стационарных значений:
exp монотонен, поэтому g_sp < 0 ⟺ exp(−g_sp) > 1 ⟺ g*_sp < 0, и
аналогично для g_sp > 0. Но это РАЗНЫЕ функции: g*(Y) —
ВСПОМОГАТЕЛЬНАЯ функция для итераций, НЕ исходная TPD; её значения
вне стационарных точек не являются dG/RT, а стационарные значения
связаны с g нелинейно (1 − exp(−g_sp)). НЕ называть g*(Y) исходной
TPD-функцией; для классификации используется ЗНАК (любой из двух
эквивалентных способов), а сравнение величин — только в терминах g.

**Тривиальная стационарная точка.** w = z даёт k = 0 и Y_i = z_i;
g = g* = 0 — НО только для ИДЕНТИЧНОГО состояния (та же ветвь корня
PR, см. §1.4/§2.1): точный +0 тривиального случая относится к
идентичным feed/trial-состояниям.

**Утверждение о линейности удалено.** Прежняя формулировка
ревизии называла целевую функцию в ненормированных переменных
«линейной по W» — это неверно (члены ln W_i нелинейны) и удалена.

**Обновление successive substitution.** Из нулевой формы
стационарного условия:

```
ln Y_i^(k+1) = h_i − lnPhi_i( w^(k) ),   w^(k) = Y^(k) / SUM_j Y_j^(k)
```

PR-состояние (lnPhi_i) пересчитывается по НОРМИРОВАННОМУ составу
w^(k); итерационные переменные Y остаются НЕнормированными
(ΣY — оценка «мольного количества» пробной фазы; 1 − ΣY = g*
в стационарной точке). Оба уровня разделены явно: PR и evaluator
получают составы, итерации ведутся в Y. Тривиальный старт w = z
(на ветви feed) — неподвижная точка SS-обновления
(ln Y^(1) = ln z + lnPhi(z) − lnPhi(z) = ln z), что используется
как smoke-проверка итерационной механики (§2.1).

Граничные стационарные точки лежат на гранях носителя: на
подмножестве активных компонентов условие выполняется с теми же
свойствами, поиск на грани — §5.

### 1.4. Роль ветви корня PR

lnPhi_i(w) берётся из PR-состояния пробной фазы с выбранной ветвью
корня: `vapor` — наибольший физический корень, `liquid` — наименьший
(контракт 4.4.4.3: selectedRoot = physical[last] для vapor,
physical[0] для liquid). Физический фильтр Z > B НЕ ограничивает
число физических корней двумя: при D < 0 кубика имеет ровно три
различимых действительных корня, и все три могут быть больше B
(контрольный расчёт CO₂, §3); промежуточный физический корень
идентификатором ветви НЕ снабжается и отдельной попыткой поиска НЕ
обследуется (корректировка топологии корней, §3). Ветвь — часть
моделирования ПРОБНОЙ фазы;
выбор ветви сам по себе НЕ является ни доказательством существования
такой фазы, ни доказательством устойчивости/неустойчивости.

**Идентичность состояния требует одну и ту же ветвь.** Точный
TPD = +0 тривиального случая относится к идентичным feed/trial-
состояниям: побитово одинаковые T/P/evidencePolicy/a_i/b_i/kij И
одна и та же ветвь корня PR. Одинаковый состав w = z, вычисленный
на ДРУГОЙ ветви корня, — ДРУГОЕ состояние: корень кубики и lnPhi
могут различаться, TPD НЕ обязан быть нулём и обязан вычисляться
штатно. Такая точка — самостоятельная допустимая пробная точка: она
НЕ исключается из проверки отрицательности на основании равенства
составов и НЕ получает автоматически статус тривиального
TPD(z; z) = +0 (старт feed_alternative_branch, §2.1).

### 1.5. Стационарная точка ≠ доказанный глобальный минимум

Локальные методы сходятся к ОДНОЙ стационарной точке на начальное
приближение; TPD-функция может иметь несколько стационарных точек,
а локальный минимум может не быть глобальным (пятая
корректирующая ревизия: текущий 4.4.4.4.2 использует ТОЛЬКО
successive substitution, §2.4–2.5; safeguarded Newton/BFGS —
возможные будущие локальные методы из отдельного fallback-подэтапа,
вне текущего объёма, НЕ влияющие на текущие формулы и счётчики
бюджета). Поэтому:

- надёжно отрицательное TPD в любой ДОПУСТИМОЙ корректно
  вычисленной ПОСЕЩЁННОЙ точке (не только в сошедшейся
  стационарной) — ДОСТАТОЧНОЕ свидетельство неустойчивости
  feed-фазы в рамках PR-модели: глобальный минимум искать не
  требуется, он не выше найденного значения; сходимость породившей
  попытки НЕ требуется (§6.6). «Надёжно отрицательная» —
  СТРОГОЕ понятие (четвёртая корректирующая ревизия): точка
  класса C1, установленная ТОЛЬКО по доступному
  validated numerical error bound (§6.5, §6.6); эмпирическое
  наблюдение отрицательности (observed envelope, §6.5) само по
  себе НЕ является строгим доказательством знака и НЕ даёт
  `unstable_detected`;
- неотрицательное TPD во всех НАЙДЕННЫХ точках НЕ доказывает
  глобальной устойчивости: конечный набор стартов и итераций не
  гарантирует полноты (см. §6.6, семантика
  `no_instability_found_within_search`).

## 2. Начальные приближения

### 2.1. Обязательный набор стартовых точек

Поиск выполняется из НЕСКОЛЬКИХ детерминированных стартовых точек;
один старт (в любом направлении) НЕ считается достаточным
обоснованием полноты поиска. Предлагаемый минимальный набор для
носителя supp(z) из s компонентов (на полном носителе; построение
на гранях — §5):

1. **`feed`** — w = z на ветви FEED. Тривиальный старт:
   неподвижная точка SS (§1.3), TPD = ровно +0 идентичного
   состояния. Включается как базовая попытка (smoke-проверка
   сходимости итерационной механики), но тривиальный результат не
   считается «найденным нетривиальным минимумом» и не может дать
   `unstable_detected`.
2. **`feed_alternative_branch`** — w = z на АЛЬТЕРНАТИВНОЙ ветви
   корня PR (если `hasDistinctBranches`; при единственном
   физическом корне старт не создаётся — ветвь одна, см. §3). Тот
   же состав — ДРУГОЕ состояние: вычисляется штатно через PR на
   альтернативной ветви и оценивается evaluator'ом; TPD НЕ
   предполагается нулём (§1.4) и НЕ исключается из проверки
   отрицательности.
3. **`wilson_z_times_k`** — Wilson-направление Y^(0) = z·K:
   ln Y_i^(0) = ln z_i + ln K_i (при K_i > 1 у лёгких компонентов —
   обогащение лёгкими; масштаб Y^(0) сохраняется, нормировка w^(0) —
   §2.3). НЕ «паровая фаза»: универсальное фазовое имя НЕ
   назначается — физическая интерпретация зависит от принятой
   конвенции K-value (конвенция ниже).
4. **`wilson_z_over_k`** — Wilson-направление Y^(0) = z/K:
   ln Y_i^(0) = ln z_i − ln K_i (обеднение лёгкими компонентами;
   масштаб Y^(0) сохраняется, нормировка w^(0) — §2.3). НЕ
   «жидкая фаза»: универсальное фазовое имя НЕ назначается —
   физическая интерпретация зависит от принятой конвенции K-value
   (конвенция ниже).
5. **`uniform`** — равномерный состав по носителю: w_i = 1/s.
6. **`pair_{i,j}`** — парные составы w_i = w_j = 0.5 для каждой
   упорядоченной пары i < j из supp(z) (O(s^2) точек,
   детерминированный порядок).

**Конвенция Wilson-направлений (третья корректирующая ревизия).**
Идентификаторы стартов НЕЙТРАЛЬНЫ и описывают только ФОРМУЛУ:
`wilson_z_times_k` (Y = z·K) и `wilson_z_over_k` (Y = z/K). Это
ДВА НЕЗАВИСИМЫХ Wilson-направления, ОБЯЗАТЕЛЬНЫХ оба; универсальные
названия «паровая»/«жидкая» фаза им НЕ назначаются: физическая
интерпретация состава зависит от принятой конвенции K-value и от
типа исходного feed, а литература использует для тех же формул
РАЗНЫЕ словесные метки: по двустороннему уравнению Michelsen
(§0, пункт 5) жидкоподобный feed → пробная фаза Y_i = z_i·K_i,
пароподобный feed → Y_i = z_i/K_i; GEOS (§0, пункт 3) называет
y = z/K «lighter trial mixture», а y = z·K — «heavier trial
mixture» — в ОБРАТНОМ словесном порядке относительно
паро-/жидкоподобной терминологии. Поэтому словесные метки
(light/heavy, vapor-like/liquid-like) НЕ используются ни в API,
ни в именах стартов. Факты формулы сохраняются: Wilson K_i > 1 у
лёгких компонентов, поэтому z·K обогащает состав лёгкими
компонентами, z/K — обедняет. Литература прямо отмечает
зависимость результата stability analysis от начальных K-values
(§0, пункт 4).

### 2.2. Wilson K-values: доступность данных (проверено)

Корреляция Wilson (1969):

```
K_i = (Pc_i / P) · exp( 5.373 · (1 + omega_i) · (1 − Tc_i / T) )
```

Требуемые Tc_i, Pc_i, omega_i УЖЕ доступны в контракте 4.4.4.3:
`PengRobinsonMixtureComponentInput` содержит `criticalTemperatureK`,
`criticalPressurePa`, `acentricFactor` (вместе с moleFraction,
per-field evidence, crossChecks, limitations) — это те же
валидированные каталогом (4.4.4.1) параметры, которые evidencePolicy
уже приняла при расчёте feed-состояния. Wilson starts НЕ требуют
нового provenance и НЕ вводят новых чисел: они переиспользуют
принятые параметры. Если политика отклонила параметры какого-то
компонента, PR-расчёт feed невозможен и поиск не начинается вовсе
(отказ раньше). Никакие параметры не восстанавливаются и не
выдумываются. Благодаря единому источнику истины входов (§4.3)
Wilson starts структурно НЕ могут использовать параметры, не
соответствующие feed.

### 2.3. Ненормированный масштаб Y и log-space построение стартов

Вектор Michelsen Y — НЕнормированные псевдомольные количества
(§1.3); АБСОЛЮТНЫЙ масштаб Wilson-старта несёт информацию и НЕ
должен теряться при формировании старта. Всё построение ведётся
сразу в логарифмах, БЕЗ промежуточного exp для K:

```
ln K_i = ln(Pc_i) − ln(P) + 5.373 · (1 + omega_i) · (1 − Tc_i / T)
```

исходное состояние итерационной переменной:

- `wilson_z_times_k`: ln Y_i^(0) = ln z_i + ln K_i
  (ненормированный вектор z·K);
- `wilson_z_over_k`: ln Y_i^(0) = ln z_i − ln K_i
  (ненормированный вектор z/K);

нормировка — только для передачи в PR/evaluator:

```
ln w_i^(0) = ln Y_i^(0) − logsumexp( ln Y^(0) )
```

**ТРИ ОТДЕЛЬНЫХ правила** (обязательны для реализации):

1. **ln Y^(0) сохраняется как исходное состояние итерационной
   переменной попытки**: абсолютный масштаб z·K или z/K (ΣY^(0) ≠ 1
   в общем случае) — начальная оценка «мольного количества» пробной
   фазы (§1.3) и передаётся в SS-итерации (§2.4);
2. **в PR-пересчёт и TPD-evaluator передаётся ТОЛЬКО нормированный
   w^(0) = Y^(0)/ΣY^(0)** (и нормированные составы всех
   последующих итераций);
3. **successive substitution обновляет НЕнормированный Y**
   (§1.3: ln Y_i^(k+1) = h_i − lnPhi_i(w^(k))), а не нормированный
   w.

**ЗАПРЕЩЕНО**: сначала нормализовать Wilson Y (w = Y/ΣY) и затем
использовать Y = w как начальное состояние итераций — это теряет
исходный масштаб z_i·K_i или z_i/K_i и даёт ДРУГОЕ начальное
состояние (ΣY^(0) = 1); итерации обязаны стартовать с сохранённого
ln Y^(0).

**Масштаб Y^(0) остальных стартов** (единообразно и
детерминированно): для стартов, задаваемых только составом (`feed`,
`feed_alternative_branch`, `uniform`, `pair_{i,j}`, feed-restricted
на гранях §5), принимается Y^(0) = w^(0), ΣY^(0) = 1. Для `feed`
это согласовано с тривиальной неподвижной точкой SS (§1.3:
ln Y^(1) = ln z).

Это исключает и переполнение/исчезновение при экстремальных K, и
epsilon-подмену: члены с z_i = 0 в носитель не входят
(структурно, §1.2), z_i > 0 гарантирует конечный ln z_i.
Компоненты с выродившимся (ноль после нормировки в double) w_i
просто не входят в пробный носитель — support-контракт evaluator
обрабатывает это штатно.

### 2.4. Итерации successive substitution и оценка траектории

Каждая попытка стартует с сохранённого ln Y^(0) (§2.3) и ведёт
SS-итерации по §1.3: нормировка Y → w, PR-пересчёт по w (та же
ветвь корня, те же T/P/kij, §4.2), SS-обновление в НЕнормированном
Y. **Каждая допустимая посещённая точка оценивается существующим
TPD-evaluator'ом** (feed-состояние против текущей trial-точки) —
это принцип 4.4.4.4.2: любая допустимая корректно вычисленная
точка остаётся ПРОБНОЙ точкой и участвует в bestVisitedPoint и
проверке отрицательности (строгой — по validatedErrorBound,
§6.5–§6.6; для будущего fallback-подэтапа, §2.5,
принцип сохраняется: точка, отвергнутая как оптимизационный шаг,
НЕ теряется как пробная точка). Попытка накапливает:

- минимальный TPD, встреченный за ВСЮ траекторию попытки
  (bestVisitedPoint), с составом соответствующей точки, ветвью
  корня, номером итерации, вкладами компонентов, идентификатором
  старта и подмножеством носителя;
- финальную стационарную точку (finalStationaryPoint) — только если
  попытка сошлась (§6.1/§6.3).

Разделение обязательно: bestVisitedPoint и finalStationaryPoint —
РАЗНЫЕ записи; минимум траектории может достигаться в промежуточной
итерации, а не в финальной точке. Если попытка позже НЕ сошлась,
уже обнаруженные отрицательные значения НЕ теряются: они остаются
в bestVisitedPoint попытки и в глобальном bestVisitedTpd поиска
(§7.2) и могут давать `unstable_detected` (§6.6).

### 2.5. Fallback: ВНЕ объёма 4.4.4.4.2 (третья корректирующая ревизия)

Прежний текст предлагал ЛОКАЛЬНЫЙ safeguarded fallback (BFGS ИЛИ
safeguarded Newton) внутри 4.4.4.4.2 без фиксации единственного
алгоритма, критерия принятия шага и точного бюджета — это
НЕДООПРЕДЕЛЁННАЯ спецификация, и fallback УДАЛЁН из обязательного
объёма 4.4.4.4.2 (вариант A, предпочтительный для первой
реализации):

- **объём 4.4.4.4.2 — ТОЛЬКО successive substitution** (§1.3,
  §2.4) с фиксированным бюджетом N_max SS-обновлений на попытку
  (§6.2);
- несходимость после исчерпания N_max → outcome `max_iterations` →
  вклад в `indeterminate` (§6.6; приоритет класса C1
  сохраняется);
- никаких fallback/Jacobian/line-search вызовов в 4.4.4.4.2 НЕТ:
  бюджет и счётчики (§4.4) считаются ТОЛЬКО по SS;
- fallback отложен в ОТДЕЛЬНЫЙ будущий подэтап. При его отдельном
  старте спецификация ДОЛЖНА будет зафиксировать: ОДИН конкретный
  алгоритм (не «BFGS или Newton»), явную merit/residual-функцию,
  метод и порядок вычисления якобиана (аналитические производные
  lnPhi по составу в проекте НЕ реализованы — якобиан только
  численный), line-search acceptance rule, ТОЧНЫЕ максимумы
  PR-вызовов на якобиан, шаг и line-search (включая отказные),
  пересчитанный maxPrEvaluations для всех случаев и гарантию, что
  все допустимые точки Jacobian/line-search оцениваются
  TPD-evaluator'ом и участвуют в bestVisitedPoint (§2.4);
- глобальные методы (туннелирование, интервальный анализ,
  стохастика) НЕ предлагаются; невозможность гарантировать
  глобальный минимум закрыта семантикой
  `no_instability_found_within_search`, а не алгоритмом.

## 3. Ветви корня PR

**Разведение счётчиков: physicalRootCount ≠ searchBranchCount
(корректировка топологии корней 2026-11-06; проверено по
фактическому коду 4.4.4.2/4.4.4.3 — `solvePrCubicRealRoots`,
`prPhysicalRoots`, `PengRobinsonMixtureSuccess`).**

- **`physicalRootCount`** — ФАКТИЧЕСКОЕ число корней, возвращённых
  физическим фильтром PR (`prPhysicalRoots`: строго Z > B,
  сортировка по возрастанию). Ограничения «не более двух» в
  контракте НЕТ: при D < 0 кубика имеет ровно три различимых
  действительных корня, и все три могут быть больше B.
  Контрольный расчёт (чистый CO₂ из каталога 4.4.4.1:
  Tc = 304.1282 K, pc = 7377300 Pa, omega = 0.22394; T = 250 K,
  P = 1 MPa): A = 0.1042200, B = 0.0128292,
  Z = 0.0198964 / 0.0652088 / 0.9020656 — все три корня > B,
  physicalRootCount = 3.
- **`searchBranchCount`** — число ветвей, которые TPD-поиск
  ДЕЙСТВИТЕЛЬНО обследует через существующий интерфейс
  `root = 'vapor' | 'liquid'`: `vapor` выбирает НАИБОЛЬШИЙ
  физический корень (selectedRoot = physical[last]), `liquid` —
  НАИМЕНЬШИЙ (physical[0]). Для состава c:
  `searchBranchCount_c = min(physicalRootCount_c, 2)`.
- **Принятая политика (обоснована существующим API, зафиксирована
  как ЯВНОЕ ОГРАНИЧЕНИЕ поиска):** промежуточные физические корни
  (physicalRootCount = 3) НЕ создают отдельных попыток — текущий
  PR-API не предоставляет отдельного идентификатора ветви для
  каждого физического корня. Промежуточный корень НЕ считается
  обследованным отдельной trial-ветвью; `searchBranchCount` НЕ
  называется числом физических корней; `branchCoverageComplete`
  относится ТОЛЬКО к двум предусмотренным внешним ветвям поиска
  (vapor/liquid) всех обязательных составов, а НЕ к каждому корню
  `physicalRoots` (см. п. 8). Поисковые заключения — утверждения
  об обследованных ветвях поиска в рамках выполненного перебора.
  PR runtime-контракт (4.4.4.3) этой корректировкой НЕ меняется.

1. **Корни определяются ПОШАТОВНО, для каждого уникального
   стартового состава (третья корректирующая ревизия).** PR-кубика
   смеси имеет до ТРЁХ различимых действительных корней (D < 0;
   физический фильтр Z > B не ограничивает двумя, см. вводный
   блок), и число корней
   ЗАВИСИТ от состава пробной фазы: его НЕЛЬЗЯ считать единым
   свойством подмножества стартов S (старты одного подмножества
   имеют разные составы, корней может быть разное число).
   Обязательный порядок для КАЖДОГО уникального стартового
   состава:
   - выполнить начальный PR-пересчёт ИМЕННО этого состава
     (T, P, kij входа, §4.2) и определить фактическое число
     физических корней physicalRootCount_c по ЭТОМУ результату
     (`distinctPhysicalRootCount`, `hasDistinctBranches`,
     контракт 4.4.4.3; может быть 1, 2 или 3), а также число
     обследуемых ветвей поиска
     searchBranchCount_c = min(physicalRootCount_c, 2);
   - при searchBranchCount_c = 2 (physicalRootCount_c = 2 ИЛИ
     3) — создать ДВЕ независимые попытки, по одной на каждую
     ВЕТВЬ ПОИСКА (logicalLabels ['vapor'] и ['liquid'],
     разные selectedRoot — наибольший и наименьший физический
     корень), каждая со своими траекториями и бюджетом; при
     physicalRootCount_c = 3 промежуточный физический корень
     НЕ образует третьей попытки (принятая политика вводного
     блока: идентификатора ветви для него в API нет);
   - при searchBranchCount_c = 1 (physicalRootCount_c = 1) —
     создать ОДНУ попытку: не запускать две
     одинаковые PR-попытки под метками vapor/liquid и не
     дедуплицировать постфактум. Запись попытки хранит:
     `logicalLabels: ['vapor', 'liquid']` (обе логические метки
     ссылаются на один и тот же корень), `selectedRoot`
     (фактически выбранный физический корень кубики, Z),
     `singlePhysicalRoot: true`. Предупреждение
     `single_physical_root` (4.4.4.3) сохраняется в notes
     результата. Дублирования результата, искусственного
     двойного счёта попыток и двойного расхода бюджета НЕТ.
2. **Одна попытка на одну уникальную ветвь поиска**
   — обязательное правило (без изменений): каждая попытка
   привязана к ОДНОЙ ветви поиска — уникальному логическому
   идентификатору `vapor`/`liquid`, который через существующий
   PR-API выбирает ОДИН физический корень кубики (наибольший /
   наименьший; при трёх физических корнях промежуточный корень
   ни одной попытке не принадлежит).
3. **Изменение числа корней в ходе итераций.** Траектория попытки
   меняет состав w; PR-кубика на новом составе может иметь ДРУГОЕ
   число физических корней, чем на старте. В каждой посещённой
   точке (§7.2) сохраняется фактический `selectedRoot`,
   фактические root labels и `physicalRootCount`; факт изменения
   числа физических корней в ходе итераций отражается в
   метаданных посещённой точки (§7.2). Если корни совпали в ходе
   ранее созданных попыток, искусственная независимая ветвь НЕ
   создаётся: попытка продолжает итерироваться на фактическом
   единственном корне.
4. **Отказ branch-specific initial call при успешном discovery
   (пятая корректирующая ревизия).** Первый успешный PR-вызов
   состава определил physicalRootCount_c и searchBranchCount_c.
   Если searchBranchCount_c = 2, ОБА начальных
   branch-specific состояния обязательны:
   - отказ PR-вызова для второй ветви учитывается в
     `prEvaluations` (§4.4);
   - отказ НЕ означает, что вторая ветвь автоматически покрыта:
     `branchCoverageComplete = false`, пока обязательная ветвь
     не рассчитана успешно;
   - без другой допустимой C1-точки (по validated bound, §6.5–6.6)
     итог — `indeterminate` с явной причиной.
5. **Отказ root-discovery-вызова (пятая корректирующая
   ревизия).** Если начальный PR-вызов состава завершился отказом
   ДО получения `physicalRoots`/`distinctPhysicalRootCount`, то
   physicalRootCount_c и searchBranchCount_c НЕИЗВЕСТНЫ.
   Обязательное поведение (fail-closed, без
   подмен):
   - НЕ подставлять `searchBranchCount_c = 1` (и
     `physicalRootCount_c = 1`) и НЕ объявлять ветвевое покрытие
     этого состава полным;
   - НЕ создавать фиктивный `singlePhysicalRoot` и НЕ запускать
     SS-итерации без корректного начального PR-состояния;
   - отказ сохраняется в счётчике PR (`prEvaluations`, §4.4);
   - записывается явная причина `root_discovery_failure`;
   - `branchCoverageComplete = false` для этого обязательного
     состава;
   - без другой допустимой C1-точки итог — `indeterminate` с
     причиной `root_discovery_failure` (§6.6).
6. **Root-branch continuation при двух начальных ветвях поиска
   (четвёртая
   корректирующая ревизия).** Используется существующая семантика
   PR-контракта 4.4.4.3 (§1.4): `vapor` — НАИБОЛЬШИЙ физический
   корень, `liquid` — НАИМЕНЬШИЙ; при одном физическом корне обе
   логические метки ссылаются на один корень. Попытки, созданные
   при searchBranchCount_c = 2 (п. 1), получают УСТОЙЧИВЫЕ
   логические
   идентификаторы ветви (`vapor` / `liquid`), которые СОХРАНЯЮТСЯ
   на всей траектории:
   - при каждом новом составе PR вызывается с trial request
     `root = continuationBranch` попытки (§7.1; ветвь попытки),
     а фактические `selectedRoot`,
     `rootLabels`, `physicalRootCount` сохраняются для конкретной
     посещённой точки;
   - если в некоторой точке физический корень только один, обе
     логические ветви в этой точке соответствуют одному
     фактическому корню, а `rootLabels` фактического единственного
     корня отражают ОБЕ логические метки;
   - ДВЕ истории попыток сохраняются: не удаляются и не
     склеиваются постфактум;
   - если корни впоследствии снова разделяются (2 → 1 → 2), каждая
     попытка продолжает СВОЮ логическую ветвь через существующий
     выбор `vapor`/`liquid` (каждая возвращается к своему корню:
     наибольшему / наименьшему соответственно).
7. **Root-branch continuation при раздвоении однокорневой попытки
   (вариант A, четвёртая корректирующая ревизия; уточнение
   пятой; корректировка топологии корней).** Попытка,
   начатая с ОДНОГО физического корня (logicalLabels =
   ['vapor', 'liquid'], п. 1), при возникновении в ходе итераций
   НЕСКОЛЬКИХ физических корней (два или три) уже НЕ может
   одновременно представлять все ветви поиска. Для первой версии
   выбран безопасный вариант A:
   - динамический fork попыток НЕ создаётся;
   - траектория продолжается по ОДНОЙ детерминированной ветви —
     continuation branch = `continuationBranch` попытки,
     определённый однозначно по согласованному правилу §7.1
     (= `feedRoot`, значение `request.root` входа);
   - прочие возникшие ветви поиска (и промежуточные физические
     корни, не имеющие идентификатора ветви) ЯВНО зафиксированы
     как необследованные;
   - семантика меток (пятая ревизия): `logicalLabels` попытки
     описывает НАЧАЛЬНУЮ эквивалентность (обе метки одного
     корня), но `rootLabels` посещённой МНОГОКОРНЕВОЙ точки
     отражает ТОЛЬКО реально выбранную continuation branch;
     необследованные прочие ветви фиксируются явно,
     `branchCoverageComplete = false`;
   - на уровне результата выставляется `branchCoverageComplete =
     false` (§7.2), `no_instability_found_within_search`
     ЗАПРЕЩЁН; при отсутствии допустимой точки C1 итог —
     `indeterminate` с причиной `branch_coverage_incomplete`
     (§6.6);
   - допустимая точка C1 (по validated bound, §6.5–6.6) сохраняет
     ПРИОРИТЕТ и даёт `unstable_detected` даже при неполном
     покрытии ветвей.
8. **Полнота граней ≠ полнота ветвей.** `faceEnumeration`
   описывает полноту перебора ПОДМНОЖЕСТВ носителя (§5), а
   `branchCoverageComplete` — полноту покрытия ВЕТВЕЙ ПОИСКА:
   двух предусмотренных внешних ветвей (`vapor`/`liquid`) всех
   обязательных стартовых составов, а НЕ каждого физического
   корня `physicalRoots` (промежуточный корень при трёх
   физических корнях ветви поиска НЕ образует, вводный блок §3);
   это НЕЗАВИСИМЫЕ свойства, и полнота первого НЕ
   даёт полноты второго. Вывод о полноте поиска только на
   основании `faceEnumeration = 'complete'` НЕДОПУСТИМ (§6.6).
9. **Feed-ветвь** фиксирована входом вызывающего кода
   (`request.root` = feedRoot, §7.1) и не перебирается; старт
   `feed_alternative_branch` (§2.1) покрывает ПРОТИВОПОЛОЖНУЮ
   ветвь поиска тем же составом z (при наличии альтернативной
   ветви — physicalRootCount >= 2) через trial request с
   противоположной feedRoot ветвью (§7.1).
10. Выбор ветви — моделирование пробной фазы, НЕ доказательство её
   физического существования и НЕ доказательство устойчивости
   (идентификаторы `vapor`/`liquid` — только ветви PR-кубики:
   наибольший/наименьший физический корень, НЕ термодинамическая
   стабильность; промежуточные физические корни идентификатором
   ветви НЕ снабжаются; §1.4).

## 4. Архитектура Core/Data (проверено по фактическому коду)

### 4.1. Доступные данные (проверено)

Из `PengRobinsonMixtureSuccess` (4.4.4.3) доступны: `a_i`, `b_i`,
`S_i`, `lnPhi_i`, `phi_i`, `f_i` по компонентам;
`binaryInteractionsUsed` (значение kij, evidence,
applicabilityRangeK по использованным парам);
`physicalRoots`, `distinctPhysicalRootCount`, `hasDistinctBranches`,
`selectedRoot`, `Z`; предупреждения (включая
`single_physical_root`, `h2o_classical_pr_limitations`). Из
Data-фасада (`computePengRobinsonMixtureFromCatalog`) дополнительно
доступны provenance-скаляры `componentParameters` /
`binaryInteractionParameters`. Контракт применимости kij по
температуре нарушать нельзя: выход пары за `applicabilityRangeK` —
отказ `binary_interaction_applicability`, kij = 0 НЕ
подставляется.

### 4.2. Пересчёт PR для нового trial-состава

Пересчёт PR-состояния пробной фазы при неизменных T/P и тех же
параметрах взаимодействия — тот же вызов `computePengRobinsonMixture`
(4.4.4.3) с ТЕМИ ЖЕ `components` (те же идентификаторы, Tc/Pc/omega,
evidence, crossChecks, limitations; меняются только moleFraction)
и `binaryInteractions`, что и для feed, и request
`{ temperatureK, pressurePa, root, evidencePolicy }`. Provenance НЕ
нарушается: параметры те же, уже принятые политикой; новых чисел не
возникает; evidencePolicy применяется к каждому пересчёту
одинаково. TPD-evaluator 4.4.4.4.1 получает уже вычисленные
состояния и побитово сверяет T/P/evidencePolicy/a_i/b_i/kij-пары —
контракт 4.4.4.4.1 остаётся без изменений.

### 4.3. Единый источник истины входов (корректирующая ревизия)

Прежняя схема API (отдельно `feed: PengRobinsonMixtureSuccess`,
отдельно `components`, отдельно `binaryInteractions`) отвергнута:
`PengRobinsonMixtureSuccess` НЕ содержит полного исходного набора
(Tc/Pc/omega с per-field evidence, crossChecks, limitations),
поэтому независимые массивы могли — случайно или намеренно — не
соответствовать параметрам, из которых был получен feed.

Выбран проверяемый единый источник истины:

- **Core-search принимает ПОЛНЫЕ исходные `PengRobinsonMixtureInputs`
  ({components — включая moleFraction feed-состава, evidence,
  crossChecks, limitations — и binaryInteractions}) и
  `PengRobinsonMixtureRequest` {temperatureK, pressurePa,
  root = feedRoot, evidencePolicy} и САМ пересчитывает авторитетное
  feed-состояние через `computePengRobinsonMixture` до начала
  поиска.** Согласованность обеспечивается by construction: нет
  второго источника параметров, который мог бы разойтись; Wilson
  starts могут использовать ТОЛЬКО те же компонентные входы
  (§2.2); trial-пересчёты — копии тех же inputs с изменённым
  moleFraction (§4.2).
- Альтернатива (передавать и feed success, и полные inputs, затем
  пересчитывать feed из inputs и сверять с переданным до поиска)
  отвергнута: побитовая сверка полного success-объекта хрупка и
  дороже, чем построение feed из единого входа, и оставляет
  два источника истины на входе.
- Контракт существующего TPD-evaluator НЕ меняется: он по-прежнему
  получает ДВА уже вычисленных состояния (feed и trial), которые
  готовит оркестратор (§4.2); любое изменение его контракта —
  отдельное обоснование и отдельный этап.

### 4.4. Детерминированность и вычислительный бюджет

- Поиск полностью детерминирован: фиксированный порядок
  подмножеств, стартов и уникальных корней; никакого рандома;
  повторный вызов с тем же входом даёт побитово тот же результат.
- **faceCount** — число непустых СОБСТВЕННЫХ подмножеств носителя
  (граней): 2^s − 2, где s = |supp(z)|; вместе с полным носителем
  поиск покрывает 2^s − 1 подмножеств. faceCount — НЕ число
  итерационных запусков: 30 граней при s = 5 — это СТРУКТУРА
  перебора, а не «30 попыток».
- **attemptCount** = Σ по уникальным стартовым составам c поиска
  (уникальные составы после дедупликации §5) × searchBranchCount_c,
  где searchBranchCount_c — число ВЕТВЕЙ ПОИСКА (vapor/liquid),
  обследуемых для состава c через существующий PR-API
  (§3, вводный блок: searchBranchCount_c =
  min(physicalRootCount_c, 2); 1 при единственном физическом
  корне, 2 при двух ИЛИ трёх физических корнях — промежуточный
  корень ветви поиска НЕ образует). searchBranchCount_c — НЕ
  число физических корней: physicalRootCount_c может быть 3.
  Число корней определяется ПОШАТОВНО для каждого
  уникального стартового состава — НЕ один раз для всего
  подмножества S: у стартов одного подмножества могут быть
  разные physicalRootCount_c / searchBranchCount_c.
- **Единое правило подсчёта PR-вызовов**: считаются ВСЕ фактические
  вызовы `computePengRobinsonMixture` поиска, включая
  завершившиеся отказом (fail-closed отказы расходуют бюджет
  наравне с успешными); переиспользование уже вычисленного
  состояния (например, авторитетного feed-состояния для старта
  `feed` на ветви feed) НЕ считается новым вызовом.
- **maxPrEvaluations (четвёртая корректирующая ревизия —
  ветве-специфичные начальные вызовы; корректировка топологии
  корней — счётчик ветвей поиска).** Прежняя формула
  1 + Σ_c [init_c + r_c·N_max] НЕДОСТАТОЧНА при
  searchBranchCount_c = 2: по
  фактическому контракту Core (`pengRobinsonMixture.ts`)
  `physicalRoots`/`distinctPhysicalRootCount` сообщают о
  физических корнях (их может быть до трёх), `selectedRoot`
  выбирается по `root`
  соответствующего PR request (для trial-попыток — root =
  continuationBranch, §7.1),
  а компонентные `lnPhi` вычисляются для ВЫБРАННОГО Z, но НЕ
  одновременно для всех ветвей. Один discovery-вызов НЕ
  предоставляет начальное PR-состояние для каждой ветви. Для
  каждого уникального стартового состава c:
  - `searchBranchCount_c` — число обследуемых ВЕТВЕЙ ПОИСКА
    состава c (§3, вводный блок): min(physicalRootCount_c, 2);
    НЕ число физических корней (physicalRootCount_c может
    быть 3 — промежуточный корень не создаёт ветви поиска);
  - `feedReuse_c` = 1, ТОЛЬКО если уже вычисленное авторитетное
    feed-состояние действительно побитово совместимо по составу,
    T/P, kij, evidencePolicy И выбранной ветви и переиспользуется
    как начальное состояние одной из попыток; иначе
    `feedReuse_c` = 0;
  - `initialBranchCalls_c = searchBranchCount_c − feedReuse_c` —
    число PR-вызовов,
    необходимое для получения начальных состояний ВСЕХ ветвей
    состава c.

  При одном общем начальном авторитетном feed-вызове:

  ```
  maxPrEvaluations = 1 + Σ_c [ initialBranchCalls_c + searchBranchCount_c · N_max ]
  ```

  В бюджет входят ВСЕ фактические вызовы
  `computePengRobinsonMixture` поиска — ровно четыре категории:
  1. авторитетный feed PR-расчёт (слагаемое 1);
  2. начальные PR-состояния КАЖДОГО нового стартового состава и
     КАЖДОЙ его ветви поиска (`initialBranchCalls_c`): для
     нового состава с searchBranchCount_c = 2 первый PR-вызов
     одновременно
     обнаруживает число корней и инициализирует одну выбранную
     ветвь, а для второй ветви нужен ЕЩЁ ОДИН PR-вызов; для
     feed-состава начальная ветвь может переиспользовать уже
     существующий feed PR-результат (`feedReuse_c` = 1), но
     альтернативная ветвь ВСЁ РАВНО требует собственного
     начального пересчёта;
  3. SS-обновления каждой попытки (`searchBranchCount_c · N_max`,
     §6.2);
  4. вызовы, завершившиеся ОТКАЗОМ, — расходуют бюджет наравне с
     успешными (fail-closed).

  Переиспользование уже вычисленного состояния НЕ считается новым
  вызовом. Fallback в 4.4.4.4.2 ОТСУТСТВУЕТ (§2.5), численный
  якобиан и line-search НЕ используются — отдельных слагаемых на
  них НЕТ. Формула детерминирована по входу и проверяема
  тестами (§7.3).
- **Бюджет при неудавшемся root-discovery (пятая корректирующая
  ревизия; корректировка топологии корней — переименование).**
  Формула с фактическим `searchBranchCount_c` применима ТОЛЬКО
  после успешного обнаружения числа корней. Если discovery-вызов
  состава завершился отказом (§3, п. 5) и
  `physicalRootCount_c`/`searchBranchCount_c` неизвестны,
  для этого состава действует КОНСЕРВАТИВНЫЙ ВЕРХНИЙ ПРЕДЕЛ
  бюджета по максимуму ОБСЛЕДУЕМЫХ ВЕТВЕЙ ПОИСКА
  `searchBranchMax = 2` (прежде `r_max`; переименование
  существенно: 2 — максимум числа ветвей поиска, которые
  существующий root-интерфейс `vapor`/`liquid` позволяет
  обследовать, НЕ максимум физического числа корней —
  физических корней может быть три, но ветвей поиска через
  текущий API не более двух, §3):

  ```
  maxPrEvaluations = 1 + Σ_{c: discovery ok} [ initialBranchCalls_c + searchBranchCount_c · N_max ]
                   + Σ_{c: discovery failed} [ searchBranchMax + searchBranchMax · N_max ],  searchBranchMax = 2
  ```

  Разводятся ЧЕТЫРЕ раздельных понятия (не смешивать):
  1. **максимально допустимый бюджет** `maxPrEvaluations` —
     консервативный верхний предел, вычисляемый независимо от
     фактических отказов; для неудавшегося discovery он НЕ
     уменьшается и НЕ «пересчитывается постфактум» под
     фактически потраченные вызовы;
  2. **фактические PR-вызовы** `prEvaluations` — только
     действительно выполненные вызовы (для неудавшегося
     discovery-состава: 1 отказавший вызов; попыток и
     SS-итераций этого состава НЕТ);
  3. **неудавшиеся начальные вызовы** — расходуют бюджет
     наравне с успешными (fail-closed, категория 4 выше);
  4. **отсутствие возможности продолжить конкретный состав** —
     НЕ уменьшает лимит бюджета: лимит остаётся
     консервативным, `prEvaluations <= maxPrEvaluations`
     выполняется всегда; переполнение бюджета и искусственное
     уменьшение лимита после отказа НЕ допускаются
     (проверяется тестами, §7.3).
- Результат ОБЯЗАН возвращать фактические счётчики: faceCount,
  attemptCount, prEvaluations и maxPrEvaluations (§7.2); тесты
  фиксируют prEvaluations <= maxPrEvaluations (§7.3).
- Для каталога (s <= 5) полное перечисление граней стоит
  faceCount <= 30 и attemptCount, вычисляемый по формуле выше
  (после дедупликации — меньше); точные числа выводятся из формул
  в момент исполнения и не заявляются константами.

## 5. Границы симплекса

1. **Внутренний поиск**: старты §2.1 на полном носителе supp(z);
   SS-итерации §1.3 сохраняют носитель (ln Y_i конечен при z_i > 0).
2. **Грани носителя**: минимум TPD может лежать на грани (часть
   W_i = 0). Стратегия: тот же поиск (старты + SS) выполняется на
   каждом собственном непустом подмножестве носителя. Построение
   стартов на грани S ⊆ supp(z):
   - feed-restricted: z|_S, нормированный по S (Y^(0) = w^(0),
     ΣY^(0) = 1, §2.3);
   - wilson_z_times_k / wilson_z_over_k: ln Y^(0) =
     ln z|_S ± ln K (ненормированный масштаб сохраняется, §2.3),
     нормировка по S — только для w^(0);
   - uniform: 1/|S| на S (Y^(0) = w^(0));
   - pair_{i,j} внутри S (Y^(0) = w^(0)).
   **Правила дедупликации стартов**: старты с побитово равными
   стартовыми векторами состава, на том же подмножестве и против
   того же уникального корня исполняются ОДИН раз (каноническая
   сериализация как ключ дедупликации). Примеры: |S| = 1 — все
   старты совпадают с единственной вершиной (1 запуск);
   |S| = 2 — uniform совпадает с pair (не удваивает бюджет).
   Перечисление граней: полное при s <= 5 (каталог — потолок,
   faceCount <= 30); при s > 5 — детерминированная выборка граней
   (например, все грани размера s−1 и s−2) и ЧЕСТНАЯ маркировка
   `faceEnumeration: 'partial'` с перечнем обследованных
   подмножеств.
3. **Вырождение на границе итераций**: если SS-итерация загоняет
   компонент к нулю (w_i → 0 в double), попытка завершается на
   достигнутой точке, и старт повторяется на соответствующей грани —
   граничный минимум ищется штатным поиском грани, а не
   «дотяжкой» нуля.
4. **Честная маркировка**: результат всегда содержит
   `faceEnumeration` ('complete' | 'partial') и список обследованных
   подмножеств. Поиск только по внутренним точкам НЕ выдаёт
   формулировку, эквивалентную доказательству глобальной
   устойчивости: `no_instability_found_within_search` описывает
   РЕАЛЬНО выполненный поиск и только его.

## 6. Сходимость и численная классификация

### 6.1. Stationarity tolerance

Невязка стационарности на финальной нормированной точке попытки
(все активные i, §1.3):

```
b_i = ln w_i + lnPhi_i(w) − h_i,   k̂ = SUM_i w_i · b_i (= g),
r_stat = max_i | b_i − k̂ |
```

(в стационарной точке все b_i равны одной константе k = g).
Предложение: **sigma_stat = 1e−10**. Обоснование: невязка на 4–6
порядков выше машинного шума итераций (ulp-масштаб lnPhi ~1e-16) и
на несколько порядков ниже любого физически осмысленного масштаба
lnPhi (O(0.1–10)). Значение — инженерный допуск сходимости;
ПОЛНАЯ погрешность TPD — отдельный вопрос §6.5.

### 6.2. Лимит итераций (SS-only, третья корректирующая ревизия)

Fallback удалён из объёма 4.4.4.4.2 (§2.5, вариант A), поэтому
прежние раздельные резервы N_SS_max/N_fallback_max/N_total_max
заменены ОДНИМ лимитом. Предложение (предварительное значение
спецификации, §8):

- **N_max = 300** SS-обновлений на попытку (уникальный стартовый
  состав × ветвь поиска, §3–4.4);
- итерация, не удовлетворившая критериям §6.1–6.4 после
  исчерпания N_max, даёт outcome `max_iterations` попытки → вклад
  в `indeterminate` результата (§6.6; приоритет класса C1
  сохраняется);
- fallback/Jacobian/line-search вызовов НЕТ (§2.5), бюджет
  попытки — только SS: N_max PR-пересчётов + начальные
  PR-расчёты всех ветвей поиска состава (initialBranchCalls_c, §4.4;
  при searchBranchCount_c = 2 — два ветве-специфичных
  начальных вызова минус
  переиспользование feed-состояния, feedReuse_c); превышение
  maxPrEvaluations невозможно по
  построению и проверяется тестами (§7.3).

Обоснование N_max: SS сходится линейно; 300 итераций покрывают
и медленные случаи, и остаются дешёвыми в детерминированном
бюджете (§4.4). Литературные лимиты (сотни итераций) подтверждают
порядок величины; точное значение — наше, по бюджету. Бюджет
попытки входит в maxPrEvaluations по формуле §4.4.

### 6.3. Критерий изменения состава

Предложение: **sigma_w = 1e−12** в log-space (переменные Y, §1.3):
`max_i |ln Y_i^(k+1) − ln Y_i^(k)| <= 1e−12`. Состав отслеживается
в логарифмах, поэтому критерий бережёт малые доли от ложной
сходимости по абсолютной дельте.

### 6.4. Критерий изменения TPD

Предложение: **sigma_tpd = 1e−12**:
`|TPD^(k+1) − TPD^(k)| <= 1e−12` при масштабе вкладов O(1).
Критерий контролирует стагнацию СУММЫ; попытка считается
сошедшейся только при выполнении 6.1 И 6.3; 6.4 — дополнительный
стоп-сигнал и НЕ даёт права на заключение без 6.1.

### 6.5. Отрицательный TPD threshold (корректирующая ревизия)

**Статус: ПРЕДВАРИТЕЛЬНОЕ, НЕУТВЕРЖДЁННОЕ предложение.**
`t_neg = −1e−10` — рабочее предварительное значение для тестов и
первой реализации, НЕ научно доказанная граница. Порог −1e−8 из
внешних реализаций НЕ копируется (проигрывает умеренной, но реальной
неустойчивости ~ −1e−9); уверенность в −1e−10 НЕ заявляется.

**Раздельные понятия** (не смешивать; третья и четвёртая
корректирующие ревизии):

1. **оценка TPD** — скаляр tpdEstimate существующего evaluator
   4.4.4.4.1 в точке;
2. **observedErrorEnvelope** — эмпирический наблюдаемый максимум
   ошибки на конечной audit-матрице, применимый ТОЛЬКО внутри
   audit-domain. Это ДИАГНОСТИЧЕСКИЙ ориентир: он НЕ является
   доказанной верхней границей ошибки и НЕ называется
   «консервативной оценкой неопределённости». Сам по себе он НЕ
   даёт права объявить точку «надёжно отрицательной» или «надёжно
   неотрицательной»;
3. **validatedErrorBound** — отдельный объект: математически
   доказанная численная граница ошибки (validated numerics,
   интервальные оценки или доказанный анализ обусловленности) с
   собственной областью применимости. ТОЛЬКО он допускается для
   строгой interval-based классификации знака (классы C1–C4,
   §6.6). Пока validated bound не установлен, эмпирический
   envelope используется только как диагностический ориентир и
   НИКОГДА не заменяет bound;
4. **предварительный operational margin t_neg = −1e−10** —
   отдельное предварительное значение «достаточного отрицательного
   запаса», НЕ оценка точности;
5. **знак TPD** в строгом смысле классифицируется ТОЛЬКО
   интервально по validatedErrorBound (§6.6):
   [tpdEstimate − validatedErrorBound, tpdEstimate +
   validatedErrorBound]; эмпирический интервал
   [tpdEstimate ± observedErrorEnvelope] — диагностическое
   значение, сохраняемое в точке;
6. **невязка стационарности r_stat** (§6.1) — качество
   сходимости итераций, а НЕ погрешность вычисленного TPD уже
   посещённой точки: r_stat НЕ входит НИ в observedErrorEnvelope,
   НИ в validatedErrorBound и НЕ складывается с арифметической
   ошибкой evaluator; учитывается в критериях сходимости попытки
   и в исходе `indeterminate` (§6.2, §6.6).

**Декомпозиция погрешностей** (раздельно, без смешения):

1. вычисление ln(w/z) в evaluator 4.4.4.4.1 — устойчивая форма
   (w===z, log1p, fallback разности логарифмов);
   регрессионно охарактеризована, вносит ошибку много меньше
   1e−15 при вкладах O(1);
2. суммирование вкладов — компенсированная сумма Neumaier;
   регрессионно охарактеризована (малые TPD до ~1e−22 в близких
   составах разрешаются);
3. PR-кубика смеси и выбор физического корня — решатель 4.4.4.2.2
   (DD + dyadic-BigInt-знак) точен в классификации корней, НО
   погрешность корня Z и её влияние на lnPhi вблизи
   вырожденных/почти кратных корней НЕ охарактеризованы
   количественно;
4. вычисление lnPhi — цепочка a_mix, S_i, ln-членов; погрешность
   НЕ охарактеризована количественно глобально;
5. итерационный остаток стационарности — ограничен допуском 6.1
   (1e−10), НЕ нулевой; это качество сходимости итераций, НЕ
   арифметическая погрешность TPD точки: НЕ входит НИ в
   observedErrorEnvelope, НИ в validatedErrorBound («Раздельные
   понятия», п. 6).

Точность арифметики evaluator в отдельных регрессионных тестах НЕ
доказывает глобальную погрешность PR lnPhi и корней кубики вблизи
вырожденных случаев. Прежнее утверждение ревизии о полной ошибке
PR-вычисления TPD «~1e−13» УДАЛЕНО как неподтверждённое измерениями.

**План количественного аудита** (обязателен до утверждения
порога; независимый от реализации поиска):

- высокоточный oracle для PR mixture (прецедент: независимые
  бенчмарки 4.4.4.2.2/4.4.4.3 с mpmath/CoolProp);
- смеси разной размерности (2–5 компонентов: реальный каталог и
  синтетика);
- обычные two-root состояния И режимы около слияния физических
  корней (почти кратные корни кубики); классификация точек
  audit-матрицы по режиму корней подчиняется строгому правилу
  кратности (§7.2 п. 4.1): без multiplicity/discriminant данных
  PR-контракта точки с physicalRootCount 1 или 2 НЕ могут быть
  проверяемо отнесены к не-near-merge режиму — это ограничение
  действует и для самого аудита;
- составы с долями, близкими к нулю, и сильно неравномерные;
- независимое сравнение итогового TPD и отдельных вкладов
  компонентов против oracle;
- итог аудита: **empirical observed error envelope — наблюдаемый
  максимум ошибки на заранее заданной audit-матрице**
  (observedErrorEnvelope) вместе с **машинно-проверяемым
  описанием audit-domain** (`AuditDomainDescriptor`, §7.2:
  диапазоны T и P, допустимая размерность смеси, ограничения по
  составам/малодольным компонентам, режим физических корней
  включая близость к слиянию, применимость использованных BIP и
  их evidence-политика, идентичность EOS/BIP-набора по
  каноническому fingerprint (п. 4.2 в §7.2); ЧИСЛЕННЫЕ ГРАНИЦЫ остаются null до
  реального аудита — никаких придуманных чисел). Терминология
  разделяет ТРИ разных понятия: (i) empirical observed error
  envelope — эмпирический факт об audit-матрице, ДИАГНОСТИЧЕСКИЙ
  ориентир, НЕ доказанная верхняя граница и НЕ «консервативная
  оценка неопределённости»; (ii) validated numerical error bound —
  доказанная граница (validated numerics, интервальные оценки или
  доказанный анализ обусловленности), допустимая для строгой
  классификации C1–C4 (§6.6); (iii) provisional operational
  margin t_neg (§6.5). Envelope действителен ТОЛЬКО внутри
  audit-domain и вне его НЕ применяется;
- **применимость к точке (машинно-проверяемая, четвёртая
  ревизия; раздельные домены — пятая)**: детерминированный
  предикат `isWithinAuditDomain`
  (§7.2) получает PR/TPD-состояние точки и дескриптор домена и
  проверяет ВСЕ условия применимости: область не задана или
  неполна (любое null-поле дескриптора) → статус оценки
  `'pending_audit'`; точка не удовлетворяет хотя бы одному
  условию → `'outside_audit_domain'` (envelope неприменим);
  точка внутри → `'observed_envelope_in_domain'` — ТОЛЬКО
  эмпирический статус, НЕ validated bound. Предикат применяется
  к `auditDomain` и `validatedDomain` РАЗДЕЛЬНО: статус
  validated bound точки вычисляется тем же предикатом против
  `validatedDomain` и НЕ выводится из статуса envelope
  (§7.2, §7.3 п. 21). Эмпирический envelope
  применим — но это по-прежнему диагностический ориентир,
  классификация относительно проверенного диапазона аудита, а не
  математическая гарантия вне его;
- **validated numerical error bound — отдельный результат
  аудита**: численный validated bound допустим ТОЛЬКО после
  отдельного аудита и обоснования (validated numerics,
  интервальные оценки, доказанный анализ обусловленности и
  погрешности по фактической декомпозиции выше) и имеет СОБственную
  область применимости (`validatedDomain`, §7.2) со своим
  per-point статусом; конечный набор oracle-тестов НЕ доказывает
  глобальную точность PR и НЕ превращает envelope в bound;
- mpmath/high-precision PR oracle — независимый числовой ОРИЕНТИР
  аудита; CoolProp — ДОПОЛНИТЕЛЬНАЯ независимая сверка там, где он
  возвращает пригодные конечные данные, но НЕ замена
  high-precision oracle;
- из observedErrorEnvelope, audit-domain и коэффициента запаса
  уточняются t_neg и ДИАГНОСТИЧЕСКИЕ границы с явной ревизией
  этого документа; СТРОГИЕ классификационные границы C1–C4 (§6.6)
  требуют отдельного validated bound; НИКАКИХ придуманных оценок
  погрешности.

**До завершения аудита (строгий вариант, четвёртая ревизия)**:
никакой validated numerical error bound НЕ установлен. Результату
возвращаются `observedErrorEnvelope: null` +
`observedErrorEnvelopeStatus: 'pending_audit'` +
`auditDomain: null` + `validatedErrorBound: null` +
`validatedErrorBoundStatus: 'pending_validation'`; каждой
посещённой точке — `observedErrorEnvelopeStatus:
'pending_audit'` и `validatedErrorBoundStatus:
'not_established'` (§7.2). t_neg = −1e−10 действует как
предварительный operational margin с явной пометкой статуса
(`negativeThresholdStatus`, §7.2). СТРОГОЕ СЛЕДСТВИЕ принятого
варианта: пока validated bound не установлен, НИ одна точка не
может быть классифицирована как C1 или C4, и ЛЮБОЙ поиск
возвращает `indeterminate` — консервативно и осознанно; успешный
CI или отсутствие отказов НЕ меняют этого. Значения, знак
которых нельзя надёжно классифицировать, НЕ дают права на
`unstable_detected` и ведут к `indeterminate` (§6.6). При этом
диагностические значения НЕ теряются: tpdEstimate, вклады,
bestVisitedTpd, bestVisitedPoint сохраняются в результате, а
после завершения эмпирического аудита — и диагностический
интервал [tpdEstimate ± observedErrorEnvelope] точек внутри
audit-domain: потенциально интересная отрицательная точка
остаётся видимой для оператора, даже когда эмпирический
интервал не пересекает ноль, но verdict остаётся
`indeterminate` (§6.6). Никаких фиктивных ошибок и выдуманных
гарантий точности: точность evaluator — факт регрессий;
глобальная точность PR-TPD — предмет аудита; validated bound —
отдельный будущий результат, а не переименованный envelope.

### 6.6. Семантика результатов (имена согласованы с SCOPE_NOTE 4.4.4.4.1)

Единый консервативный контракт (корректирующие ревизии; первая
удалила формулировку, допускавшую `no_instability_found_within_search`
при исчерпанном бюджете без сходимости; вторая устранила дыру, в
которой надёжно отрицательное TPD МЕЖДУ t_neg и нулём не получало
ни `unstable_detected`, ни полосы неопределённости и могло
приводить к `no_instability_found_within_search`).

**Interval-based классификация знака** (§6.5; третья и четвёртая
корректирующие ревизии — точные взаимоисключающие определения,
строгий вариант): для каждой допустимой корректно вычисленной
посещённой точки с оценкой tpdEstimate и ДОСТУПНЫМ
validatedErrorBound (§6.5) обозначим L = tpdEstimate −
validatedErrorBound, U = tpdEstimate + validatedErrorBound.
Интервал [L, U] даёт класс точки:

- **C1 (надёжно отрицательная ниже margin)**: U < t_neg;
- **C2 (отрицательная без запаса)**: t_neg <= U < 0 — верхняя
  граница уже не ниже margin, но всё ещё ниже нуля;
- **C3 (знак неопределён)**: L < 0 И U >= 0 — интервал
  пересекает ноль;
- **C4 (надёжно неотрицательная)**: L >= 0.

Классы ВЗАИМОИСКЛЮЧАЮЩИ и ИСЧЕРПЫВАЮЩИ при validatedErrorBound >= 0
и t_neg < 0: U < t_neg, t_neg <= U < 0, U >= 0 с L < 0, U >= 0
с L >= 0 — четыре непересекающихся случая, покрывающих все
интервалы. Граничные случаи: точный интервал [0, 0] — ТОЛЬКО C4;
[0, positive] — C4; [negative, 0] — C3 (U = 0 попадает в C3, а
не в C4); интервал целиком ниже нуля, но не ниже t_neg — C2.
При отдельном отказе от margin (t_neg не действует) C1
вырождается в условие U < 0, а C2 становится пустым.

Классификация в СТРОГОМ смысле требует ДОСТУПНОГО per-point
validatedErrorBound (§6.5): точка класса C1 или C4 может быть
установлена ТОЛЬКО при validatedErrorBoundStatus =
`'validated_bound_in_domain'` — рассчитанной именно с
validated bound. Эмпирический observedErrorEnvelope сам по себе
НЕ даёт права объявлять точку «надёжно отрицательной» или
«надёжно неотрицательной»: если validated bound не установлен
(аудит не выполнен) или точка вне его области применимости
(`'outside_validated_domain'`, `'not_established'`), точка НЕ
классифицируется как C1/C4 независимо от эмпирического
интервала, и verdict деградирует до `indeterminate` с явной
причиной — консервативно и без придуманных оценок.
Диагностические значения при этом сохраняются (§6.5).

**Verdict-правила**:

- **`unstable_detected`** — найдена ДОПУСТИМАЯ корректно
  вычисленная ПОСЕЩЁННАЯ точка (стартовая, промежуточная итерация
  любой SS-попытки, §2.4) класса C1, рассчитанного С validated
  bound (§6.5). Сходимость породившей попытки НЕ требуется.
  **ПРИОРИТЕТ**: одного класса C1 достаточно для вывода о
  неустойчивости feed-фазы в рамках выбранной PR-модели и принятых
  данных — даже при наличии других неудавшихся или несошедшихся
  попыток и даже при `branchCoverageComplete = false` (§3).
- **`no_instability_found_within_search`** — ВСЕ обязательные
  попытки достигли критериев сходимости (6.1 И 6.3);
  `branchCoverageComplete = true` (ВСЕ обязательные ветви ПОИСКА
  рассчитаны, §3: полнота относится к двум предусмотренным
  внешним ветвям vapor/liquid всех обязательных составов, НЕ к
  каждому физическому корню `physicalRoots`); ВСЕ предусмотренные грани обследованы
  (faceEnumeration = 'complete' в пределах лимита перечисления —
  полнота граней НЕ заменяет полноту ветвей, §3); численных
  отказов нет; И для ВСЕХ посещённых допустимых точек установлен
  класс C4 (L >= 0) с ДОСТУПНЫМ validatedErrorBound КАЖДОЙ точке
  (`'validated_bound_in_domain'`, §6.5). Отсутствие validated
  bound хотя бы для одной точки, эмпирический envelope без
  validated bound, неполное покрытие ветвей или граней —
  надёжное `no_instability_found_within_search` НЕ выдаётся:
  исход классифицируется как `indeterminate` с явной причиной.
  Отрицательное TPD между t_neg и нулём (класс C2) НЕ приводит к
  `no_instability_found_within_search` НИ ПРИ КАКИХ условиях. Это
  НЕ доказательство глобальной устойчивости: формулировка
  описывает только выполненный поиск.
- **`indeterminate`** — класса C1 нет, НО: есть точка класса C2
  (недостаточный отрицательный запас) или C3 (знак неопределён);
  ИЛИ хотя бы одна обязательная попытка не сошлась
  (max_iterations), завершилась numerical_failure или была
  недопустима; ИЛИ обязательная ветвь не рассчитана /
  однокорневая попытка встретила появление нескольких
  физических корней
  (`branchCoverageComplete = false`, причина
  `branch_coverage_incomplete`, §3), в том числе отказ
  branch-specific начального вызова ветви (§3, п. 4) или отказ
  root-discovery-вызова состава (§3, п. 5, причина
  `root_discovery_failure`); ИЛИ перечисление граней
  осталось неполным сверх лимита; ИЛИ validatedErrorBound хотя бы
  одной точки недоступен (не установлен или точка вне его
  области применимости, §6.5), в том числе имеется ТОЛЬКО
  эмпирический envelope без validated bound — даже если
  эмпирический интервал не пересекает ноль.
- Статус `stable` НЕ выдаётся ни при каких условиях. Математическая
  глобальная полнота конечного multi-start НЕ утверждается. Имена
  перечислены в PR_TANGENT_PLANE_DISTANCE_SCOPE_NOTE (границы
  4.4.4.4.1), где зафиксировано, что сам evaluator их не выдаёт:
  поисковые заключения — предмет 4.4.4.4.2.

### 7.1. Вход (TypeScript-предложение)

```ts
interface PrTangentPlaneDistanceSearchInput {
  /**
   * ПОЛНЫЕ исходные входы PR-смеси 4.4.4.3 — единый источник
   * истины (§4.3): components (с feed-составом, Tc/Pc/omega,

   */
  mixtureInputs: PengRobinsonMixtureInputs;

   * оркестратор пересчитывает САМ из mixtureInputs (§4.3).
   * request.root — ЭТО feedRoot: он определяет ТОЛЬКО ветвь
   * авторитетного feed PR-состояния и НЕ является ветвью

   */
  request: PengRobinsonMixtureRequest; // root = feedRoot

```

**Разделение feed request root и branch-specific trial request
(пятая корректирующая ревизия).** Верхнеуровневый `request.root`
(= `feedRoot`, §7.2) задаёт ветвь ТОЛЬКО авторитетного FEED-расчёта.
Для каждой trial-попытки оркестратор создаёт ОТДЕЛЬНЫЙ PR request
с теми же `temperatureK`/`pressurePa`/`evidencePolicy` и с
`root = attempt.continuationBranch` (§3, §7.2):

- при двух начальных ветвях поиска (searchBranchCount_c = 2;
  физических корней два ИЛИ три, §3): попытка ветви `vapor`
  использует trial request `root = 'vapor'`, попытка ветви
  `liquid` — trial request `root = 'liquid'`;
- при старте `feed_alternative_branch` начальное PR-состояние
  получает ПРОТИВОПОЛОЖНУЮ feed-ветвь (например, при
  feedRoot = 'vapor' — `root = 'liquid'`); переиспользовать
  авторитетный feed PR success можно ТОЛЬКО для совпадающей
  ветви (feedReuse_c, §4.4), альтернативная ветвь ВСЕГДА
  требует собственного пересчёта;
- при одном начальном физическом корне `initialBranch = 'single'`,
  а `continuationBranch` определяется однозначно по согласованному
  правилу: `continuationBranch = feedRoot` (значение request.root
  входа); именно эта ветвь используется вариантом A при
  последующем раздвоении (§3, п. 7), динамический fork не
  создаётся;
- смешивание feed request root и trial attempt root НЕ
  допускается и проверяется тестом (§7.3).

Отказы всего поиска — существующие коды: `invalid_input`,
`incompatible_state`, `support_violation`, `numerical_failure`
(например: авторитетный feed-расчёт не успех; пустой носитель;
неприемлемые политикой параметры). Никакого отдельного
feed-success или независимых массивов параметров на входе НЕТ —
схема исключает рассинхрон по построению.

```ts
 * каждому домену ОТДЕЛЬНО, результаты НЕ смешиваются (п. 5).
 */
function isWithinAuditDomain(
  point: {
    temperatureK: number;          // фактическая T точки
    pressurePa: number;            // фактическое P точки
    composition: number[];         // нормированный состав w точки
    physicalRootCount: number;    // 1, 2 или 3 фактических физических корня в этой точке (фильтр Z > B не ограничивает двумя, §3)

                                   // физическими корнями точки (для трёх корней —
                                   // минимум по соседним парам отсортированного

  domain: AuditDomainDescriptor,

```

**Семантика полей и логика предиката (пятая корректирующая
ревизия).**

**п. 4.1 — physicalRootMode (семантика; строгий вариант кратности —
корректировка топологии корней).** `twoRootCovered = true` —
well-separated двух-/трёхкорневые состояния (два или три
различимых физических корня с min попарного расстояния >=
nearMergeSeparationTolerance) покрыты аудитом;
`nearRootMergeCovered = true` — режимы ОКОЛО слияния
(различимые физические корни с min попарного расстояния <
nearMergeSeparationTolerance, включая точные кратные корни)
покрыты аудитом; `nearMergeSeparationTolerance` — конечное
числовое значение допуска (>= 0), разграничивающее эти режимы;
проверка near-merge ТОЛЬКО по |Z_vap − Z_liq| НЕ является
достаточной (см. ниже). ПОЛНЫЙ дескриптор требует ВСЕ ЧЕТЫРЕ
поля не-null; в частности,
при `nearRootMergeCovered = false` (near-merge НЕ покрыт)
`nearMergeSeparationTolerance` всё равно ОБЯЗАН быть конечным:
без конечного tolerance границу near-merge режима проверить
НЕЛЬЗЯ, и null НЕ является одновременно «корректным отрицанием
покрытия» и полным дескриптором — такой дескриптор неполон →
`pending_audit`. Числовые значения границ НЕ придумываются:
tolerance устанавливается только реальным аудитом.

`multiplicityModeAvailable` — проверяемая информация о режиме
дискриминанта/кратности кубики (п. 4.3, проверка 7).
ФАКТИЧЕСКОЕ состояние контракта 4.4.4.3 (проверено по коду
`solvePrCubicRealRoots`): multiplicity metadata в
`PengRobinsonMixtureSuccess` ОТСУТСТВУЕТ — при точном D = 0
двойной корень возвращается ОДНИМ значением (вместе с простым
корнем — два значения), тройной корень — одним значением;
знак дискриминанта не сообщается. Следствия (строгий вариант,
п. 4.3): `physicalRootCount = 1` НЕ доказывает отсутствие
near-merge/кратного корня (тройной корень неотличим от
одинокого действительного корня при D > 0); расстояние между
двумя различными возвращёнными корнями НЕ обязательно
показывает расстояние сливающейся пары (пара может быть
двойным корнем при точном D = 0, а сливающаяся пара —
внутри возвращаемого значения); неизвестная кратность НЕ
интерпретируется как отсутствие near-merge; эмпирическая
оценка НЕ выдаётся за validated bound. Пока PR-контракт не
предоставляет такую информацию, точки, чей near-merge режим
невыводим проверяемо из доступных данных, НЕ проходят
`validatedDomain` (п. 4.3). Для будущего расширения validated
domain PR-контракту потребуются: (a) проверяемый знак
дискриминанта кубики (или эквивалентная классификация режима:
один действительный корень / двойной + простой / тройной /
три различимых); (b) multiplicity metadata для каждого
возвращённого корня; с этими сведениями
`multiplicityModeAvailable = true` и near-merge режим точки
определяется проверяемо для всех случаев, включая
physicalRootCount 1 и 2. PR runtime-контракт этой
документальной корректировкой НЕ меняется; расширение —
предмет будущего подэтапа с отдельным обоснованием.

**п. 4.2 — канонический fingerprint PR-входа.** Название
источника BIP НЕ достаточно: аудит обязан покрывать КОНКРЕТНЫЙ
набор EOS/BIP-параметров. Fingerprint строится детерминированно
из ПОЛНОГО фактического PR-входа точки:
1. компоненты сортируются по каноническому идентификатору
   (лексикографически), для каждого берутся фактические
   применённые значения Tc/Pc/omega (moleFraction НЕ входит —
   состав проверяется отдельно compositionConstraints), их
   evidence-статусы и provenance-атрибуты в объёме,
   необходимом для проверки audit-domain;
2. binaryInteractions сортируются по каноническому pair ID
   (`«i|j»`, i < j лексикографически), для каждой пары —
   фактическое значение kij, source, evidence-status и
   applicabilityRangeK;
3. каноническая сериализация: детерминированный порядок ключей,
   стабильное строковое представление чисел (одна и та же
   нормализация, без локали), никаких NaN/Infinity;
4. fingerprint = SHA-256 сериализованной строки; сравнение —
   ТОЛЬКО побитовое равенство fingerprint.
Дескриптор хранит `allowedPrInputFingerprints` — список
fingerprint'ов наборов, покрытых аудитом; точка входит в домен
только при точном совпадении её `prInputFingerprint` с одним из
них (плюс `allowedComponentIds` и `allowedBipPairIds` для
независимой проверки состава пар). Поля, которые нельзя
проверить или которые не покрыты аудитом, остаются null →
дескриптор неполон → validated bound/envelope для такой точки
недоступны. Новые числа и EOS/BIP-данные НЕ вводятся.

**п. 4.3 — пошаговая логика предиката.** Проверки выполняются
в фиксированном порядке; любая неуспешная → вне домена
(при полном дескрипторе):
1. дескриптор ПОЛОН: ни одно поле/секция не null — иначе
   предикат неприменим → `'pending_audit'` (НЕ `'outside'`);
2. все числовые значения точки конечны (T, P, доли,
   minPhysicalRootSeparation, tolerance);
3. min <= max в каждом диапазоне (иначе дескриптор некорректен
   → неполон);
4. T > 0 и P > 0; T/P точки внутри диапазонов ВКЛЮЧИТЕЛЬНО;
5. component count — целое, в допустимом диапазоне;
6. все ненулевые доли >= minNonZeroMoleFraction;
   largest/smallest >= maxLargestToSmallestRatio — обе границы
   включительны;
7. root mode (строгая семантика кратности, п. 4.1; проверка
   near-merge ТОЛЬКО по |Z_vap − Z_liq| НЕдостаточна):
   - physicalRootCount = 3: доказано D < 0 (ровно три
     различимых действительных корня; ветви D = 0 и D > 0
     возвращают не более двух и одного значений
     соответственно, п. 4.1) — все действительные корни
     физические; min попарного расстояния конечен;
     separation >= tolerance → near-merge исключён
     проверяемо, требуется twoRootCovered = true;
     separation < tolerance → near-merge подтверждён
     данными, требуется nearRootMergeCovered = true, иначе
     вне домена;
   - physicalRootCount = 1 или 2 при
     multiplicityModeAvailable = false (фактический
     PR-контракт): near-merge режим НЕвыводим проверяемо из
     доступных данных — один возвращённый корень может быть
     тройным (точное D = 0) или точкой около слияния; два
     возвращённых корня могут быть парой (двойной, простой)
     при точном D = 0, и их расстояние НЕ измеряет
     расстояние сливающейся пары; неизвестная кратность НЕ
     интерпретируется как отсутствие near-merge →
     при полном дескрипторе точка НЕ проходит домен
     ('outside_audit_domain' для auditDomain /
     'outside_validated_domain' для validatedDomain);
   - physicalRootCount = 1 или 2 при
     multiplicityModeAvailable = true (будущее расширение
     PR-контракта, п. 4.1): режим определяется по
     проверяемым данным о дискриминанте/кратности; правила
     НЕ смягчаются: near-merge точки по-прежнему требуют
     nearRootMergeCovered = true;
   - physicalRootCount = 1 → minPhysicalRootSeparation ДОЛЖЕН
     быть null (не-null при одном корне — некорректное
     состояние → вне домена), twoRootCovered проверяется
     только для отсутствия противоречия;
   - separation = null при physicalRootCount >= 2 — информация
     о расстоянии отсутствует: при полном дескрипторе точка
     вне домена (данные о расстоянии нужны для определения
     режима), при неполном дескрипторе — 'pending_audit'
     (п. 4, тест 42);
8. prInputFingerprint точки совпадает побитово с одним из
   allowedPrInputFingerprints; componentIds ⊆
   allowedComponentIds; bipPairIdsUsed ⊆ allowedBipPairIds;
   bipSourcesUsed ⊆ allowedBipSources;
9. evidencePolicy точки удовлетворяет requiredEvidencePolicy.
Полный дескриптор + хотя бы одно несоответствие →
`'outside_audit_domain'`; полное соответствие → домен
подтверждён (для auditDomain — `'observed_envelope_in_domain'`,
для validatedDomain — `'validated_bound_in_domain'`).
Предикат применяется к `auditDomain` и `validatedDomain`
РАЗДЕЛЬНО: статусы обоих видов оценки вычисляются независимо и
не выводятся друг из друга (п. 5, §7.3).

**п. 4 — minPhysicalRootSeparation (семантика null).**
`minPhysicalRootSeparation = null` означает ровно одно:
второго РАЗЛИЧНОГО физического корня в точке НЕТ
(not-applicable). При двух или трёх различных физических
корнях значение
ОБЯЗАНО быть конечным неотрицательным числом (минимум
попарных расстояний; для трёх корней — по соседним парам
отсортированного массива). Если фактический
контракт PR (4.4.4.3) НЕ предоставляет данных, необходимых для
надёжного определения near-root-merge режима (знака
дискриминанта, кратности корней или расстояния между ними; при
точном D = 0 решатель возвращает двойной корень одним
значением, тройной — одним значением, п. 4.1), это
фиксируется как явное
ОГРАНИЧЕНИЕ audit-domain: validated bound для такой точки
НЕприменим (`'outside_validated_domain'` либо
`'pending_audit'` при неполном дескрипторе), пока
соответствующая информация не доступна; отсутствие второго
различного корня НЕ подменяется произвольным числом, а
применимость near-merge области консервативно считается
неподтверждённой.

Verdict-имена — только перечисленные в §6.6; поля `stable` нет и
не появляется.

### 7.3. Тест-план (обязательный минимум)

Каждый тест фиксирует И семантику, И численные значения против
НЕЗАВИСИМЫХ оракулов (прямое вычисление формулы в тесте), никогда —
против самого производственного TPD-вычислителя.

1. **Идеальный газ / KL-предел (пятая корректирующая ревизия)**:
   lnPhi = 0; g(w; z) = KL(w||z) >= 0
   с минимумом в w = z; все попытки сходятся к тривиальной точке
   (feed — неподвижная точка SS). Тест явно задаёт ТЕСТОВЫЙ
   validatedErrorBound и validatedDomain, обоснованные
   независимым аналитическим/численным оракулом (в KL-пределе
   g = KL(w||z) вычисляется тестом напрямую, и тестовый bound
   покрывает арифметическую ошибку вычисления KL), применимые
   ко ВСЕМ посещённым точкам сценария (каждая точка:
   validatedErrorBoundStatus = 'validated_bound_in_domain',
   класс C4) → verdict `no_instability_found_within_search`.
   lnPhi = 0 НЕ считается автоматически доказательством нулевой
   ошибки всего PR/TPD-вычисления: bound задаётся тестом с
   независимым обоснованием, а не выводится из lnPhi = 0.
   NEGATIVE CONTROL: тот же идеальный газ БЕЗ validated bound
   (validatedErrorBoundStatus = 'not_established' у точек) →
   verdict `indeterminate` с явной причиной, даже если все
   попытки сошлись и KL неотрицателен во всех точках (§6.5,
   §6.6).
2. **Синтетический надёжно отрицательный TPD**: синтетическая
   конфигурация (НЕ из каталога, НЕ заявляемая как физическая) с
   TPD ~ −1e−3 в точке, которую посещает хотя бы одна попытка;
   verdict `unstable_detected`, bestVisitedTpd — класс C1
   (tpdEstimate + validatedErrorBound < t_neg при синтетическом
   validatedErrorBound, заданном тестом,
   validatedErrorBoundStatus = 'validated_bound_in_domain'). Тест
   ДОКУМЕНТИРОВАН как синтетический: механика поиска, НЕ
   экспериментальная валидация EOS.
3. **Чувствительность к начальным приближениям**: синтетический
   случай с двумя стационарными точками (разные знаки TPD):
   старты wilson_z_times_k и wilson_z_over_k сходятся к РАЗНЫМ
   точкам;
   тест фиксирует, что один старт недостаточен (без второго старта
   verdict был бы ложным), и что попытки сохраняют обе точки.
4. **Одинаковый состав на двух ветвях** (корректирующая ревизия):
   w = z на ветви feed — идентичное состояние, точный +0; ТОТ ЖЕ
   состав на альтернативной ветви (two-root конфигурация) —
   вычисленное состояние с TPD ≠ 0 в общем случае. Проверяется:
   альтернативная точка НЕ подменяется exact-zero; её TPD и
   вклады совпадают с независимым оракулом (прямой пересчёт
   формулы g); обе записи присутствуют в attempts с разными
   selectedRoot и rootLabels.
5. **Single-root и two-root**: two-root — обе ветви выполняются
   независимо (logicalLabels по одной, rootLabels различны),
   старт feed_alternative_branch присутствует; single-root — на
   каждый старт/грань РОВНО одна попытка с logicalLabels =
   ['vapor','liquid'], singlePhysicalRoot = true, предупреждение
   в notes; счётчики attemptCount/prEvaluations НЕ задвоены
   (бюджет одного исполнения, а не двух).
6. **Перестановка компонентов**: перестановка входных массивов не
   меняет verdict, bestVisitedTpd и tpd побитово (канонический
   порядок итерации).
7. **Нулевые доли и границы носителя**: z_i = 0 запрещает w_i > 0
   (`support_violation`, пробная попытка не создаётся); минимум на
   грани 2-компонентной смеси обнаруживается граничным поиском;
   faceEnumeration корректен.
8. **Отслеживание лучшей посещённой точки** (корректирующая
   ревизия): траектория, где минимум TPD достигается в
   промежуточной итерации (не в финальной): bestVisitedPoint.tpd
   <= finalStationaryPoint.tpd; состав, ветвь, номер итерации и
   вклады bestVisitedPoint сохранены; глобальный bestVisitedTpd =
   min по всем попыткам (не только сошедшим).
9. **Отрицательная точка в незавершённой попытке + приоритет
   (пятая корректирующая ревизия — все подслучаи строго по
   validatedErrorBound)**:
   (a) попытка упирается в max_iterations ПОСЛЕ посещения
   отрицательной точки → `unstable_detected` РАЗРЕШЁН только
   если эта точка имеет доступный validated bound в своей
   validatedDomain (validatedErrorBoundStatus =
   'validated_bound_in_domain') и классифицируется как C1;
   найденное значение НЕ потеряно, даже если другие попытки
   тоже неудачны;
   (b) `no_instability_found_within_search` РАЗРЕШЁН только если
   КАЖДАЯ посещённая точка имеет validated bound и класс C4,
   все обязательные попытки сошлись, branchCoverageComplete =
   true и faceEnumeration = 'complete';
   (c) без validated bound (недоступен хотя бы одной точке),
   даже при сходимости всех попыток и отсутствии отрицательных
   TPD, — результат `indeterminate`;
   (d) если есть только empirical envelope (validated bound не
   установлен), — результат `indeterminate` (§6.5, §6.6).
   Формулировки «надёжно отрицательная точка» без явного
   validated bound в тесте НЕ допускаются.
10. **Пограничные значения (interval-based классификация)**: точка
   класса C1 (U < t_neg, §6.6; U = tpdEstimate +
   validatedErrorBound, классификация ТОЛЬКО по доступному
   validated bound) → `unstable_detected`;
   точка класса C2 — надёжно отрицательная между t_neg и нулём
   (например, TPD = −5e−11 при validatedErrorBound много меньше
   1e−11) →
   `indeterminate` (недостаточный отрицательный запас) и НИКОГДА
   `no_instability_found_within_search`; точка класса C3 — интервал,
   пересекающий ноль → `indeterminate` (§6.5/§6.6).
11. **Неконечные значения**: NaN/Infinity lnPhi в PR-пересчёте →
   `numerical_failure` попытки; NaN не попадает в
   tpd/bestVisitedTpd/searchVerdict.
12. **Повторяемость**: два вызова с одним входом — побитово равные
   результаты (все поля, включая counts).
13. **Бюджет и дедупликация**: counts.faceCount/attemptCount/
   prEvaluations корректны; prEvaluations <= maxPrEvaluations;
   дедупликация стартов (|S| = 1 → один старт на грань; совпадение
   uniform/pair при |S| = 2 не удваивает бюджет).
14. **Масштаб Wilson Y** (вторая ревизия): для
   wilson_z_times_k/wilson_z_over_k начальное состояние
   итераций — ln Y^(0) = ln z ± ln K с СОХРАНЁННЫМ абсолютным
   масштабом (ΣY^(0) ≠ 1 в общем случае); в PR и evaluator входит
   ТОЛЬКО нормированный w^(0) = Y^(0)/ΣY^(0) (§2.3).
15. **Запрещённая нормализация (негативный контроль)**: нормализация
   Wilson Y с последующим использованием Y = w как начального
   состояния даёт ДРУГОЕ начальное состояние (ΣY^(0) = 1) и НЕ
   допускается: тест проверяет, что итерации стартуют с
   сохранённого ln Y^(0) (первая SS-итерация и трекинг ΣY
   согласованы с исходным масштабом z·K / z/K, а не с w) (§2.3).
16. **Механика g***: на стационарной точке ln Y + lnPhi(w) − h = 0,
   вся скобка g* равна −1, g* = 1 − ΣY = 1 − exp(−g_sp) — против
   независимого оракула в тесте (§1.3).
17. **Классификация C2**: TPD = −5e−11 при validatedErrorBound,
   существенно меньшем 1e−11, НЕ даёт
   `no_instability_found_within_search` (см. п. 10).
18. **Классификация C3**: интервал [L, U] посещённой точки,
   построенный по ДОСТУПНОМУ validatedErrorBound, пересекает
   ноль → `indeterminate`; эмпирический интервал
   (observedErrorEnvelope) диагностический и C3 по нему не
   устанавливается (§6.6).
19. **Классификация C4 + сходимость**: все интервалы посещённых TPD
   неотрицательны, все обязательные попытки сошлись,
   validatedErrorBound доступен каждой точке
   → `no_instability_found_within_search`; при недоступном
   validatedErrorBound тот
   же исход → `indeterminate` с явной причиной (§6.5/§6.6).
20. **Несходимость без fallback** (третья ревизия): попытка
   исчерпывает N_max SS-обновлений без сходимости → outcome
   `max_iterations` → вклад в `indeterminate` (приоритет C1
   сохраняется: надёжно отрицательная посещённая точка даёт
   `unstable_detected` и раньше); fallback/Jacobian/line-search
   вызовов НЕТ, бюджет попытки — только SS; N_max и
   maxPrEvaluations НЕ превышены; счётчики проверяются точно,
   включая отказные PR-вызовы (§2.5, §4.4, §6.2).
21. **Раздельные auditDomain и validatedDomain (пятая
   корректирующая ревизия; прежняя формулировка третьей/четвёртой
   ошибочно приравнивала выход из auditDomain к выходу из
   validatedDomain).** Предикат isWithinAuditDomain применяется к
   каждому домену ОТДЕЛЬНО; сценарии:
   1. точка ВНЕ auditDomain, но ВНУТРИ validatedDomain:
      observedErrorEnvelopeStatus = `'outside_audit_domain'`,
      validatedErrorBoundStatus = `'validated_bound_in_domain'`,
      строгая классификация (C1/C4) ДОПУСТИМА на основании
      validated bound — эмпирический envelope неприменим, но
      строгие verdicts возможны;
   2. точка ВНУТРИ auditDomain, но ВНЕ validatedDomain:
      observedErrorEnvelopeStatus =
      `'observed_envelope_in_domain'`, validatedErrorBoundStatus =
      `'outside_validated_domain'`; эмпирический интервал —
      диагностический, строгие C1/C4 ЗАПРЕЩЕНЫ;
   3. точка ВНЕ ОБЕИХ областей: оба статуса outside; точка НЕ
      классифицируется как C1/C4 → итог `indeterminate` (если
      нет другой допустимой C1-точки с validated bound) с явной
      причиной; `no_instability_found_within_search` в
      присутствии такой точки ЗАПРЕЩЁН;
   4. дескриптор одного или обоих доменов неполон (null-поля):
      соответствующий статус `'pending_audit'` (auditDomain) или
      `'pending_validation'` (уровень результата,
      validatedErrorBoundStatus точки =
      `'not_established'`), НЕ подменяется `'outside_*'`;
      итог без установленных статусов — `indeterminate`.
   Во всех сценариях смешение результатов двух доменов НЕ
   допускается (§6.5, §6.6, §7.2).
22. **Root-метаданные точки** (вторая ревизия; уточнение
   пятой): single-root попытка
   — каждая visited point с ОДНИМ фактическим физическим корнем
   хранит фактический selectedRoot (Z) и
   rootLabels = ['vapor', 'liquid'] (обе метки одного корня);
   искусственная одиночная логическая метка НЕ назначается; если
   попытка встретила раздвоение, rootLabels ДВУХКОРНЕВОЙ точки —
   только метка continuation branch (§3, п. 7; п. 32) (§7.2).
23. **Повторяемость и точные счётчики PR**: два вызова с одним
   входом — побитово равные результаты, включая prEvaluations
   (успешные + отказные) и все счётчики бюджета (§4.4, §7.2).
24. **Взаимоисключаемость C1–C4** (третья ревизия): классы
   C1 (U < t_neg), C2 (t_neg <= U < 0), C3 (L < 0, U >= 0),
   C4 (L >= 0) взаимоисключающи и исчерпывающи при
   validatedErrorBound >= 0 и
   t_neg < 0; граничные интервалы: точный [0, 0] — ТОЛЬКО C4;
   [0, positive] — C4; [negative, 0] — C3 (не C4); интервал
   целиком ниже нуля, но U >= t_neg — C2 (§6.6).
25. **Невязка стационарности ≠ оценка ошибки** (третья ревизия;
   терминология четвёртой):
   stationarityResidual попытки НЕ входит НИ в
   observedErrorEnvelope, НИ в validatedErrorBound точки и НЕ
   складывается с арифметической неопределённостью evaluator;
   невязка влияет только на критерии сходимости (6.1) и исход
   `indeterminate`, validatedErrorBound — на интервальную
   классификацию (§6.5).
26. **Root count по стартовым составам** (третья ревизия;
   уточнение корректировки топологии корней):
   синтетический случай, где два разных стартовых состава ОДНОГО
   подмножества дают РАЗНОЕ число физических корней
   (physicalRootCount_c = 1 и physicalRootCount_c = 2):
   attemptCount и PR-бюджет считаются по-составно
   (Σ searchBranchCount_c, §4.4); single-root состав не
   удваивается; при
   изменении числа корней в ходе итераций visited point хранит
   фактический physicalRootCount (1, 2 или 3); совпавшие корни
   НЕ создают
   искусственную ветвь (§3, §7.2).
27. **Branch-specific initial PR** (четвёртая ревизия; уточнение
   пятой): новый
   стартовый состав с searchBranchCount_c = 2 — первый PR-вызов
   одновременно
   обнаруживает число корней и инициализирует ОДНУ выбранную
   ветвь; для второй ветви требуется собственный начальный
   PR-вызов (initialBranchCalls_c = 2); оба вызова расходуют
   бюджет (§4.4); отдельные сценарии отказа начального вызова —
   п. 40–41.
28. **Переиспользование ровно одного feed PR-состояния** (четвёртая
   ревизия): feed-состав — начальная ветвь переиспользует
   уже вычисленное авторитетное feed-состояние при побитовой
   совместимости состава, T/P, kij, evidencePolicy и ветви
   (feedReuse_c = 1), альтернативная ветвь получает собственный
   начальный вызов; любая несовместимость → feedReuse_c = 0 и
   полный начальный вызов (§4.4).
29. **Точное равенство бюджета**: в сценариях без раннего
   завершения и БЕЗ отказов фактические prEvaluations РАВНЫ
   maxPrEvaluations (формула §4.4), отдельно для
   searchBranchCount_c = 1 без
   reuse, searchBranchCount_c = 2 без
   reuse, searchBranchCount_c = 2 с feedReuse_c = 1; все счётчики
   детерминированы
   и воспроизводимы побитово (§4.4, §7.2). При неудавшемся
   discovery (§4.4, п. о searchBranchMax) равенство НЕ
   требуется:
   prEvaluations < maxPrEvaluations, консервативный лимит по
   searchBranchMax = 2 (максимум ВЕТВЕЙ ПОИСКА, НЕ физических
   корней) НЕ уменьшается постфактум.
30. **Отказ начального PR-вызова расходует бюджет** (четвёртая
   ревизия): начальный PR-вызов ветви, завершившийся отказом,
   увеличивает prEvaluations и учитывается в бюджете; отказ НЕ
   уменьшает maxPrEvaluations и НЕ освобождает от вызова для
   другой ветви (§4.4). Раздельные сценарии (пятая ревизия,
   §3, п. 4–5): отказ УЖЕ ИЗВЕСТНОЙ ветви при успешном
   discovery — п. 40; отказ САМОГО discovery-вызова — п. 41.
31. **Root count 2 → 1 → 2** (четвёртая ревизия): попытка,
   начатая с двумя корнями, проходит точку с единственным
   физическим корнем и затем снова раздваивается: обе истории
   попыток сохраняются (не удаляются, не склеиваются); в
   single-root точке rootLabels единственного фактического корня
   содержат обе логические метки; после повторного разделения
   каждая попытка возвращается к своей ветви vapor/liquid через
   свой trial request root = continuationBranch (§7.1);
   branchCoverageComplete остаётся true (§3, §7.2).
32. **Root count 1 → 2 без динамического fork** (четвёртая
   ревизия): single-root попытка встречает раздвоение — НОВЫЕ
   попытки НЕ создаются, траектория продолжается по одному
   детерминированному continuation branch (continuationBranch =
   feedRoot, §7.1); вторая
   возникшая ветвь явно зафиксирована как необследованная;
   branchCoverageComplete = false; при отсутствии допустимой C1
   точки итог `indeterminate` с причиной
   `branch_coverage_incomplete` (§3, §6.6, §7.2).
33. **C1 при неполном branch coverage**: попытка из п. 32
   посещает допустимую C1-точку (с validatedErrorBound) →
   приоритет C1 сохраняется, итог `unstable_detected` несмотря на
   branchCoverageComplete = false (§6.6).
34. **Полнота граней ≠ полнота ветвей**: faceEnumeration =
   'complete' при branchCoverageComplete = false НЕ даёт
   `no_instability_found_within_search` → `indeterminate` с
   причиной `branch_coverage_incomplete` (§3, §6.6).
35. **Empirical envelope без validated bound → indeterminate**
   (четвёртая ревизия): все посещённые точки имеют только
   observedErrorEnvelope в audit-domain; даже если эмпирический
   интервал НИ ОДНОЙ точки не пересекает ноль, итог
   `indeterminate`; диагностические значения (tpdEstimate,
   эмпирический интервал, bestVisitedTpd) СОХРАНЯЮТСЯ в результате;
   потенциально интересная отрицательная точка не теряется
   (§6.5, §6.6).
36. **C1/C4 только при validated bound** (четвёртая ревизия):
   строгие классы C1 и C4 вычисляются ТОЛЬКО при
   validatedErrorBoundStatus = 'validated_bound_in_domain';
   observedErrorEnvelope диагностический и сам по себе НЕ даёт
   ни `unstable_detected`, ни
   `no_instability_found_within_search` (§6.5, §6.6, §7.2).
37. **Audit-domain predicate** (четвёртая ревизия; уточнение
   пятой; корректировка топологии корней):
   isWithinAuditDomain: точка внутри — все условия выполнены;
   точка РОВНО на границе — внутри (границы включительны);
   точка за каждой из границ (T, P, размерность, минимальная
   ненулевая доля, неравномерность долей) —
   'outside_audit_domain'; близость к слиянию корней — по
   physicalRootMode СТРОГИМ правилом кратности (§7.2 п. 4.1,
   п. 4.3 проверка 7: при multiplicityModeAvailable = false
   точки с physicalRootCount 1 или 2 НЕ проходят домен —
   near-merge по их данным невыводим проверяемо; для
   physicalRootCount = 3 режим выводим по min попарного
   расстояния: при nearRootMergeCovered = false и конечном
   tolerance → near-merge точка вне domain; при tolerance =
   null — дескриптор неполон, п. 44); отсутствующая
   часть дескриптора (null) → дескриптор неполон, предикат
   неприменим, статус 'pending_audit' (§6.5, §7.2).
38. **Empirical-only не становится validated** (четвёртая
   ревизия): после применения только empirical observed error
   envelope статус validatedErrorBound остаётся
   'not_established' (per-point) и 'pending_validation'
   (уровень результата); эмпирический envelope НИКОГДА не
   повышается до validatedErrorBound без отдельного
   validated-аудита (§6.5, §7.2).
39. **Feed request root ≠ trial attempt root** (пятая
   ревизия): feedRoot (request.root входа) определяет ТОЛЬКО
   авторитетный feed-расчёт; каждая trial-попытка использует
   собственный PR request с root = attempt.continuationBranch;
   feed request root НЕ подставляется в trial-пересчёты и
   наоборот. Сценарий feedRoot = 'vapor' с двумя физическими
   корнями: авторитетный feed — root = 'vapor'; попытка старта
   `feed_alternative_branch` — trial request root = 'liquid';
   попытка ветви vapor (старт feed) переиспользует feed
   PR success только для совпадающей ветви (feedReuse_c = 1),
   ветвь liquid требует собственного пересчёта; single-root
   попытки имеют continuationBranch = feedRoot (§3, §7.1,
   §7.2).
40. **Отказ branch-specific initial call при успешном
   discovery** (пятая ревизия, §3, п. 4): discovery-вызов
   состава успешен, searchBranchCount_c = 2; начальный PR-вызов
   ВТОРОЙ ветви
   завершается отказом: отказ учтён в prEvaluations; вторая
   ветвь НЕ считается покрытой (branchCoverageComplete = false);
   фиктивное singlePhysicalRoot НЕ создаётся; без другой
   допустимой C1-точки итог `indeterminate` с явной причиной;
   бюджет НЕ уменьшен (§4.4).
41. **Отказ root-discovery-вызова** (пятая ревизия, §3, п. 5,
   §4.4): начальный PR-вызов состава завершается отказом ДО
   получения physicalRoots: searchBranchCount_c НЕ подставляется
   равным 1;
   single-root попытки и SS-итерации этого состава НЕ
   запускаются; фиктивный singlePhysicalRoot НЕ создаётся;
   причина `root_discovery_failure` записана явно;
   branchCoverageComplete = false; отказ сохранён в счётчике
   PR; maxPrEvaluations для состава — консервативный предел по
   searchBranchMax = 2 (максимум ВЕТВЕЙ ПОИСКА, НЕ физических
   корней), НЕ уменьшенный постфактум: prEvaluations <
   maxPrEvaluations; без другой допустимой C1-точки итог
   `indeterminate` (§6.6).
42. **Audit-domain: физические корни, разделение и кратность**
   (пятая ревизия; переписан корректировкой топологии корней,
   §7.2 п. 4, 4.1, 4.3 проверка 7): точка с ТРЕМЯ физическими
   корнями и конечным min попарного separation >= tolerance —
   доказано D < 0, near-merge исключён проверяемо, достаточно
   twoRootCovered = true; три корня с separation < tolerance —
   near-merge подтверждён, требуется nearRootMergeCovered =
   true, при false → вне домена; точка с ОДНИМ физическим
   корнем — minPhysicalRootSeparation = null (not-applicable),
   НО при multiplicityModeAvailable = false (фактический
   PR-контракт) отсутствие второго различного корня НЕ
   доказывает отсутствие near-merge/кратности (тройной корень
   возвращается одним значением) → точка НЕ проходит домен;
   точка с ДВУМЯ физическими корнями при
   multiplicityModeAvailable = false — два возвращённых
   значения могут быть парой (двойной, простой) при точном
   D = 0, их separation НЕ измеряет расстояние сливающейся
   пары → near-merge НЕ опровергнут, точка НЕ проходит домен
   ('outside_audit_domain' / 'outside_validated_domain' при
   полном дескрипторе); при multiplicityModeAvailable = true
   режим определяется по multiplicity/discriminant данным;
   ОТСУТСТВУЮЩАЯ
   root-separation информация при двух заявленных корнях
   (separation = null) — применимость near-merge
   консервативно неподтверждена: при nearRootMergeCovered =
   true и полном дескрипторе точка вне домена validated
   (информация о расстоянии нужна для режима), при неполном
   дескрипторе — 'pending_audit'; не-null separation при одном
   корне — некорректное состояние, вне домена.
43. **Fingerprint mismatch** (пятая ревизия, §7.2 п. 4.2):
   точка с prInputFingerprint, НЕ совпадающим ни с одним
   allowedPrInputFingerprints дескриптора (изменён чистокомпонентный
   параметр, kij, evidence-атрибут или applicabilityRangeK) →
   'outside_audit_domain' (для auditDomain) /
   'outside_validated_domain' (для validatedDomain) при полном
   дескрипторе; идентичные наборы при перестановке компонентов
   дают ОДИН canonical fingerprint (сортировка по каноническому
   ID); только совпадение названия источника BIP без
   fingerprint-совпадения проход НЕ даёт.
44. **Неполный physicalRootMode → pending_audit** (пятая
   ревизия, §7.2 п. 4.1): nearRootMergeCovered = false и
   nearMergeSeparationTolerance = null — дескриптор НЕПОЛОН
   (null не является корректным отрицанием покрытия и полным
   дескриптором одновременно) → предикат неприменим, статус
   'pending_audit', НЕ 'outside_audit_domain'; аналогично для
   любого другого null-поля дескриптора, включая
   multiplicityModeAvailable = null (корректировка топологии
   корней: доступность multiplicity/discriminant информации
   обязана быть задана явно, §7.2 п. 4.1) (§6.5, §7.2).
45. **Проверяемая идентичность компонентного набора** (пятая
   ревизия, §7.2 п. 4.2): точка с компонентом, отсутствующим в
   allowedComponentIds, или с BIP-парой вне allowedBipPairIds,
   или с evidencePolicy, не удовлетворяющей
   requiredEvidencePolicy, → вне соответствующего домена при
   полном дескрипторе; проверка выполняется независимо от
   fingerprint (каждое условие предикта §7.2 п. 4.3 отдельно
   проверяемо тестом).
46. **Три физических корня: physicalRootCount ≠
   searchBranchCount** (корректировка топологии корней, §3):
   CO₂-фикстура (чистый CO₂ каталога 4.4.4.1: Tc = 304.1282 K,
   pc = 7377300 Pa, omega = 0.22394; T = 250 K, P = 1 MPa;
   независимый оракул теста: A = 0.1042200, B = 0.0128292,
   Z = 0.0198964 / 0.0652088 / 0.9020656, все три > B):
   discovery-этап фиксирует physicalRootCount = 3
   (distinctPhysicalRootCount = 3, hasDistinctBranches =
   true); стратегия TPD обследует только крайние ветви:
   vapor = наибольший корень 0.9020656, liquid = наименьший
   0.0198964; searchBranchCount = 2; attemptCount и бюджет
   считаются по searchBranchCount_c = 2 (initialBranchCalls_c
   и searchBranchCount_c · N_max, §4.4), а НЕ по
   physicalRootCount = 3; промежуточный корень 0.0652088 ЯВНО
   НЕ считается обследованным отдельной trial-ветвью (в текущем
   PR-API нет идентификатора ветви для него); branchCoverageComplete
   НЕ требует обследования промежуточного корня (полнота —
   только по двум предусмотренным ветвям поиска, §3 п. 8);
   visited points хранят physicalRootCount = 3.
47. **Двойной корень (точное D = 0)** (корректировка топологии
   корней, §3 вводный блок, §7.2 п. 4.1): кубика с двойным
   и простым корнями: решатель
   возвращает ДВА различных значения (двойной корень — одним
   значением); multiplicity metadata в
   PengRobinsonMixtureSuccess ОТСУТСТВУЕТ: отсутствие
   multiplicity metadata запрещает считать near-merge
   validated domain проверенным только по разнице между двумя
   уникальными Z — пара (двойной, простой) имеет произвольное
   расстояние, а сливающаяся пара находится ВНУТРИ
   возвращаемого значения двойного корня; при
   multiplicityModeAvailable = false точка с
   physicalRootCount = 2 (оба значения > B) НЕ проходит
   validatedDomain при полном дескрипторе
   ('outside_validated_domain'), независимо от величины
   separation; неизвестная кратность НЕ трактуется как
   отсутствие near-merge (§7.2 п. 4.3 проверка 7).
48. **Тройной корень (точное D = 0, p = 0, q = 0)** (корректировка
   топологии корней, §7.2 п. 4.1): точный тройной корень:
   решатель возвращает ОДНО значение; один физический
   уникальный Z НЕ доказывает отсутствие кратности (тройной
   корень неотличим от одинокого действительного корня при
   D > 0 без multiplicity metadata); при
   multiplicityModeAvailable = false точка с
   physicalRootCount = 1 НЕ проходит validatedDomain при
   полном дескрипторе — validated bound для near-merge режима
   недоступен без отдельной информации о кратности (§7.2
   п. 4.3 проверка 7); расширение validated domain на такие
   точки — только после будущего расширения PR-контракта
   (сведения перечислены в §7.2 п. 4.1).

Дополнительно: отсутствие поля `stable` (фиксация множества
verdict-имён); нарушение суммы состава старта → `invalid_start`;
бюджет: фактическое число PR-пересчётов <= лимита.

## 8. Научные ограничения

1. CO2–N2 с kij = −0.017 — МОДЕЛЬНЫЙ сценарий с ограниченной
   экспериментальной опорой: статус `PARTIALLY_VERIFIED`,
   применимость 228.15–273.15 K; по Table A4 Okoro 2024 original
   PR/vdW отклоняется на 35.14%/21.31% — пара НЕ является
   количественно подтверждённой модельной системой. TPD-поиск на
   этой паре НЕ превращает её в экспериментально валидированную
   систему: любые поисковые заключения ограничены выбранной
   PR-моделью и принятыми данными.
2. НЕ импортируются: KIDA BIP, adjusted/New BIP Okoro (−0.01322 по
   Table 1; квадратичная температурная зависимость; точная
   температурная атрибуция скаляра одной Table 1 не
   устанавливается), новые EOS-значения. Evidence-статусы НЕ
   повышаются.
3. Поиск ограничен парами kij, доступными в каталоге
   (остальные пары — отказ `missing_binary_interaction`,
   kij = 0 НЕ подставляется), и применимостью kij по температуре
   (`binary_interaction_applicability`).
4. Синтетические тесты (§7.3) — проверка механики поиска, НЕ
   экспериментальная валидация EOS и НЕ свидетельство о поведении
   реальных CO2–N2.
5. Поисковые заключения `unstable_detected` /
   `no_instability_found_within_search` / `indeterminate` —
   statements о PR-модели с принятыми данными в выполненном
   поиске; глобальная устойчивость не доказывается никогда.
6. Предварительный порог отрицательности, предварительная
   диагностическая оценка observedErrorEnvelope (validated
   numerical error bound до отдельного validated-аудита
   отсутствует) и предварительный лимит бюджета
   (N_max, §6.2) — часть СПЕЦИФИКАЦИИ, а не подтверждённые
   данные: они НЕ являются
   imported-значениями, не имеют evidence-статуса и подлежат
   количественному аудиту до утверждения; каталожные значения,
   evidence и provenance этой ревизией НЕ затрагиваются.
