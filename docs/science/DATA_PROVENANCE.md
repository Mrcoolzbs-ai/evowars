## 1. Модель происхождения данных (расширение PhysValue)

Каждое научное значение в каталогах обязано иметь:

```typescript
// Проект (Stage 4.3); текущее подмножество уже есть в PhysValue
interface ProvenancedValue<T> extends PhysValue<T> {
  origin: 'observed' | 'experimental' | 'reference_range'
        | 'derived_computed' | 'numerical_approximation'
        | 'theoretical_estimate' | 'game_assumption' | 'unknown';
  sourceVersion?: string;      // 'CODATA 2022', 'ATcT ver. 1.228', 'HITRAN2024'
  sourceId?: string;           // ID записи каталога/вещества
  checkedAt?: string;          // ISO-дата проверки
  uncertaintyKind?: 'none' | 'range' | 'sigma' | 'factor' | 'qualitative';
}
```

Правила: конфликт источников не решается случайным выбором — фиксируются
происхождение, метод, диапазон, неопределённость и причина выбора (ТЗ §19.7).
`unknown` не превращается в число неявно.

**Согласование схемы §1 с реализацией (Stage 4.3.1, 2026-10-31).**
Схема `ProvenancedValue` реализована для термодинамических значений как
`ThermoDataProvenance` (`src/modules/Core/thermodynamics.ts`):
типизированное происхождение значения `origin` (`ThermoValueOrigin`:
observed / experimental / reference_range / derived_computed /
numerical_approximation / theoretical_estimate / game_assumption /
unknown; runtime-реестр `THERMO_VALUE_ORIGINS`) поверх существующей
архитектуры — без дублирования уже имеющихся полей `ScientificValue` /
`DataProvenance` / `Uncertainty`: `sourceVersion` §1 → существующее
`datasetVersion`; идентификаторы — существующие `sourceId` / `datasetId` /
`recordId`; `checkedAt` §1 → существующее `retrievedAt`;
`uncertaintyKind` §1 → существующий `Uncertainty`. Каждое известное или
оценочное термодинамическое значение несёт СОБСТВЕННЫЙ provenance
(а не только общую ссылку на источник всего вещества): для known /
estimated без содержательного происхождения валидация возвращает ошибку;
отсутствие uncertainty НЕ трактуется как нулевая погрешность; для
`unknown` числовое значение не создаётся вовсе. Реальные источники
значений не добавлены: импорт и перекрёстная проверка ≥20 видов —
подэтап 4.3.2 (NIST Chemistry WebBook SRD 69 — основной источник;
ATcT TN 1.228 — приоритетный для сопоставления ΔfH°, лицензия остаётся
unverified: данные ATcT в дистрибутив не включаются до отдельной
проверки лицензии). DOI, CAS, WebBook ID, ATcT ID, даты проверки,
неопределённости и условия применимости не выдумываются.

Корректирующая ревизия 4.3.1 (validator hardening, 2026-10-31):
per-value provenance распространён на ОТДЕЛЬНЫЕ точки исходных

## 2. Каталог научных ресурсов

### 2.1 NIST CODATA — фундаментальные константы
- **Организация**: NIST (CODATA Task Group). **URL**: https://physics.nist.gov/cuu/Constants/ (карточка CODATA 2022: physics.nist.gov/cuu/pdf/wallet_2022.pdf).
- **Тип**: справочник констант. **Покрывает**: G, σ, элементарные константы, конверсии.
- **Среды**: универсальные. **Ограничения**: рекомендованные значения с неопределённостями; G — наименее точная фундаментальная константа.
- **Версия**: **CODATA 2022** — актуальный рекомендованный набор на дату
  ревизии 30.10.2026 (проверено: публикация доступна). Следующий
  четырёхлетний выпуск (CODATA 2026) ожидается отдельно — проверить после
  официальной публикации; значение константы НЕ подменяется только из-за
  появления нового календарного года. **Публикации**: Tiesinga et al.,
  2021/2024 (Rev. Mod. Phys./arXiv:2409.03787).
- **API**: таблицы/web. **Лицензия**: данные NIST общедоступны, цитирование обязательно. **Коммерческое**: допустимо с цитированием.
- **Интеграция**: Units — заменить ярлык «CODATA 2018» на «CODATA 2022» (значения используемых констант не изменились; проверено по карточке 2022).
- **Тесты**: единичные значения констант; согласованность производных (σ против h,c,k — на уровне 4.10).

### 2.2 NIST Chemistry WebBook (SRD 69)
- **Организация**: NIST. **URL**: https://webbook.nist.gov/chemistry/.
- **Тип**: база данных. **Покрывает**: молярные массы, термохимия газовой фазы (ΔfH°, S°, Cp), ионная энергетика, фазовые переходы, Antoine-корреляции, спектры (частично).
- **Среды**: индивидуальные вещества; диапазоны для корреляций указаны по записям.
- **Версия**: живой SRD 69; последнее обновление данных — **2025** (ревизия
  4.0.1, проверено на официальной странице). При импорте значений
  фиксируются дата проверки и идентификатор конкретной записи (WebBook ID).
  **Публикации**: по каждой записи.
- **API**: HTTP-запросы по ID. **Лицензия**: общедоступные данные NIST, цитирование.
- **Интеграция**: главный источник термодинамики веществ (этап 4.3) + расширение Antoine-наборов за пределы CH₄/C₂H₆ (уже используется).
- **Тесты**: значения ΔfH°/S°/Cp при 298 K против таблиц; Antoine против точек кипения.

### 2.3 Active Thermochemical Tables (ATcT)
- **Организация**: Argonne National Laboratory. **URL**: https://atct.anl.gov/.
- **Тип**: база термохимических данных, построенная на network-анализе (ТН-сеть), с квантованными неопределённостями.
- **Версия (ревизия 4.0.2)**: **TN 1.228** — последняя выпущенная версия,
  проверено 30.10.2026 по официальной странице atct.anl.gov (перечень
  выпусков: Thermochemical Data → version 1.228; цитирование публикаций
  ATcT — «version 1.228 of the Thermochemical Network, Argonne National
  Laboratory, 2026, available at ATcT.anl.gov»). Ревизия 4.0.1 ошибочно
  указала 1.122 как последнюю — исправлено в 4.0.2. **TN 1.222, TN 1.220
  и TN 1.122** — более ранние выпуски: упоминаются только как исторические
  ссылки для воспроизводимости прежних расчётов и НЕ называются
  актуальными. TN 1.228 НЕ обязательно содержит данные для каждого
  необходимого химического вида — покрытие проверяется отдельно по каждой
  записи (отсутствующее значение → unknown, не подстановка из другого

каждая запись идентифицирует конкретную строку NUBASE2020 парой (i, s) — модель NuclideCandidate расширена полями stateIndex/stateCode (аудит R2, 2026-11-01: stateIndex 0–9, stateCode — реестр s: 0 — «», 1 m, 2 n, 3 p, 4 q, 5 r, 6 x, 8 i, 9 j; аудит R4, 2026-11-01: основание усилено полной ссылкой NubaseStateRowRef на конкретную строку источника — atomicNumber, massNumber, stateIndex, stateCode, recordId, все поля обязательны, дубликаты sibling-строк и самоссылки отклоняются); год NUBASE2020 — тропический (1 y = 365.2422 сут = 31 556 926 с), единицы y, ky, My зарегистрированы в реестре отдельно от юлианских yr/ka/Ma, 12 записей на y/ky/My перенесены без пересчёта значений и неопределённостей; ### 2.30 Чистокомпонентный Peng–Robinson — вычислитель Z, φ, f (Stage 4.4.4.2)

**Что добавлено**: `src/modules/Core/pengRobinson.ts` (экспорт
`Core/index.ts`, тесты `Tests/pengRobinson.test.ts`). Чистый компонент
из каталога 4.4.4.1 (co2, n2, ch4, h2o, ar; h2 — unknown_component),
полностью SI (T — K, P — Pa, a — Pa·m⁶/mol², b — м³/mol, f — Pa).

**Формулы — Peng & Robinson 1976**, Ind. Eng. Chem. Fundam. 15(1):59–64,
doi:10.1021/i160057a011 (первичная публикация; сверены с текстом
формул, включая κ(ω) и Zc):
- a(T) = 0.45724·R²·Tc²/Pc·α(T); b = 0.07780·R·Tc/Pc;
- κ = 0.37464 + 1.54226·ω − 0.26992·ω²; α(T) = [1 + κ(1 − √(T/Tc))]²;
- A = aP/(R²T²); B = bP/(RT);
- Z³ − (1−B)Z² + (A−3B²−2B)Z − (AB−B²−B³) = 0;
- ln φ = Z − 1 − ln(Z−B) − A/(2√2·B)·ln[(Z+(1+√2)B)/(Z+(1−√2)B)];
  φ = exp(ln φ); f = φ·P.
- R = 8.31446261815324 J/(mol·K) — ТОЧНОЕ значение СИ-2019 (N_A·k,
  обе постоянные определены точно); НЕ дублируется в pengRobinson.ts —
  импортируется из Core/thermoFunctions.ts (единая константа
  репозитория, Stage 4.3.4); таким образом PR использует ту же
  константу, что и вычислитель термодинамических функций NASA-7.

**Численная устойчивость** (обоснование выбора методов): решение
кубики через депрессированную форму y³+py+q: тригонометрический метод
при трёх действительных корнях; при единственном корне и p < 0 —
ГИПЕРБОЛИЧЕСКИЙ метод (y = −2·sgn(q)·√(−p/3)·cosh(arccosh|arg|/3)):
прямой Cardano у кратных/почти кратных корней катастрофически теряет
точность из-за сокращения −q/2 ± √D; при p ≥ 0 — стабильный Cardano:
из двух кубических корней берётся больший по модулю (слагаемые одного
знака, без сокращения), второй корень по Виету y = w − (p/3)/w.
КЛАССИФИКАЦИЯ ВЕТВИ (Stage 4.4.4.2.2) — double-double арифметика
(~106 бит: two_sum/two_prod Dekker/Knuth) из ТОЧНЫХ binary64-входов
A/B: DD-цепочка коэффициентов кубики, депрессированных p, q и
дискриминанта D (ТОЧНЫЕ DD-деления на 2/3/27, не умножения на
округлённые 1/3); знак D устанавливается уверенно при
|D| > 2⁻⁸⁴·масштаба: D > 0 — один корень, D < 0 — три корня,
точно D = 0 — кратный корень закрытой формой (двойной
y_d = −3q/(2p), простой y_s = 3q/p; тройной Z = (1−B)/3 при
p = q = 0) с DD-верификацией невязки (допуск
2⁻⁹⁰·масштаб·max(1,|Z|)³; неподтверждение — отказ); closeout
4.4.4.2.2: ВНУТРИ полосы порога |D| ≤ 2⁻⁸⁴·масштаба знак вычисляет
ТОЧНЫЙ dyadic-BigInt fallback из исходных binary64 A/B (разбор
IEEE-754 через DataView/getBigUint64; коэффициенты кубики — точные
диадические рациональные; знак числителя
Δ = c2²c1² − 4c1³ − 4c2³c0 − 27c0² + 18c2c1c0 в BigInt,
D = −Δ/108) — допуск невязки НЕ доказывает точное D = 0, и
неопределимых конечных входов НЕ остаётся; дедупликация кратных
корней с допуском
1e-8·max(1,|z_max|,B) (ошибка кратного корня ~√ε ≈ 1.5e-8); при
доказанных ТОЧНЫМ знаком БОЛЕЕ ЧЕМ ОДНОМ различимых корнях, которые
double не может разделить (расщепление пары ниже допуска
дедупликации), решатель возвращает структурный отказ
cubic_solver_failure (fail-closed — НЕ молчаливое схлопывание);
невязка
полинома контролируется для каждого корня; ln φ в log1p-формах
(ln(Z−B) = ln Z + log1p(−B/Z); лог-отношение через log1p) — нет
неустойчивости 0/0 при B → 0. Физически допустимы только корни
Z > B; vapor = наибольший допустимый, liquid = наименьший;
единственный корень используется обеими ветвями с явным
предупреждением. **Выбор ветви — математический выбор корня, НЕ
доказательство фазовой устойчивости и НЕ flash** (дисклеймер в notes
каждого результата; flash/VLE — вне подэтапа).

- a_ij(T) = (1−kij)·√(a_i(T)·a_j(T));

- S_i = Σⱼ x_j·a_ij;
- ln φ_i = (b_i/b_mix)·(Z−1) − ln(Z−B_mix) − (A_mix/(2√2·B_mix))·

### 2.32 Tangent-plane distance (Stage 4.4.4.4.1)

Реализация: `src/modules/Core/prTangentPlaneDistance.ts` (Core; без
импортов из Data), тесты —
`src/modules/Tests/prTangentPlaneDistance.test.ts`.

**Формула (Michelsen TPD)**: TPD(w; z) = SUM_{i: w_i > 0} w_i [ln w_i −
ln z_i + ln phi_i(w) − ln phi_i(z)], безразмерная величина dG/RT.
Вход — ДВА уже вычисленных успешных состояния PR-смеси (4.4.4.3) при
одинаковых T, P, evidencePolicy; повторных расчётов PR в модуле НЕТ,
давление отдельным членом не входит (одинаково в обоих состояниях и
сокращается). Сопоставление компонентов — по идентификаторам; w_i = 0
даёт ровно нулевой вклад (0·ln 0 не вычисляется); положительная
trial-доля при z_i = 0 или отсутствующем в feed компоненте —
структурный отказ support_violation. Проверки совместности: побитовые
T/P/evidencePolicy, a_i/b_i и использованные trial-пары kij (значение,
evidence, applicabilityRangeK) против feed-состояния; сумма состава —
в существующем допуске без нормализации. Коды отказов: invalid_input,
incompatible_state, support_violation, numerical_failure. TPD(z; z)
для одинаковых состояний — ровно +0 (побитово); вклады суммируются в
каноническом порядке (перестановка входных массивов не меняет
результат).

**Численная устойчивость (closeout-ревизия Stage 4.4.4.4.1,
2026-11-06; синхронизирована с кодом на HEAD 2c3e586f)**: ln(w/z)
вычисляется устойчивым helper-ом — w === z даёт ровно +0; при
конечной относительной разности |(w−z)/z| <= 0.5 — Math.log1p без
катаклизмического сокращения двух близких логарифмов; при выходе
относительной разности за порог ИЛИ её переполнении до ±Infinity
(возможно при subnormal z — доля может быть сколь угодно малой) —
fallback Math.log(w) − Math.log(z), который не строит промежуточного
отношения w/z и для конечных положительных w, z остаётся конечным
(прежняя формулировка «переполниться не может» относилась к
fallback-форме, но не к относительной разности, и удалена как
неверная в общем случае; epsilon-подмены и нормализации состава НЕТ).
Вклад вычисляется в фиксированном порядке: сначала
lnPhiDifference = lnPhiTrial − lnPhiFeed, затем
bracket = lnRatio + lnPhiDifference, затем
contribution = w·bracket. Разность lnPhi вычисляется ПЕРВОЙ: при
одинаковых значениях она точно равна нулю, и общий одинаковый
сдвиг lnPhi НЕ поглощает малый composition-член (регрессия:
lnRatio ~3.3e-12 при lnPhiTrial = lnPhiFeed = 1e8 — прежняя
лево-ассоциативная группировка (lnRatio + 1e8) − 1e8 округляла
его к нулю); математическая точность разности двух произвольных
lnPhi НЕ утверждается — гарантия только в смысле отсутствия
поглощения общего одинакового сдвига. Регрессия subnormal:
z = Number.MIN_VALUE, w = 0.5 — относительная разность
переполняется до Infinity, fallback сохраняет конечный TPD,
совпадающий с независимым оракулом; состав НЕ нормализуется и НЕ
подменяется. Итог — компенсированная сумма Neumaier (НЕ наивный
Kahan: на [1e16, 1, −1e16] Kahan может потерять единицу, Neumaier
сохраняет итог 1): при взаимной компенсации вкладов малых TPD
поглощение малых слагаемых восстанавливается; для близких составов
малый TPD второго порядка ~2.4e-22 разрешается формой log1p, тогда
как наивная разность логарифмов вносит шум ~1e-16. Канонический
порядок сохранён; каждый вклад доступен в contributions; неконечная
разность lnPhi, скобка, вклад или итог — явный numerical_failure
(NaN/Infinity в успехе невозможны); TPD(z; z) остаётся ровно +0.

**Границы (честно)**: модуль возвращает ТОЛЬКО скалярное значение и
вклады — БЕЗ verdict (stable/unstable/no_instability_found/
indeterminate): поиск минимумов TPD, successive substitution,
multi-start, перебор граней и доказательство глобальной устойчивости
НЕ реализованы. Семантика знака (closeout-ревизия): надёжно вычисленное
TPD(w; z) < 0 для любой допустимой пробной точки w — ДОСТАТОЧНОЕ
свидетельство неустойчивости feed-фазы в рамках выбранной PR-модели и
принятых данных; неотрицательный TPD (включая w = z, где TPD = 0) сам
по себе НЕ доказывает глобальной устойчивости — положительное
заключение требует исключить отрицательные значения на всём допустимом
пространстве пробных составов; в реальном численном поиске
отрицательность отличают от численной погрешности порогом — порог
будет частью будущего search-stage (4.4.4.4.2), НЕ этого модуля;
дизайн-спецификация будущего поиска (математический контракт,

no_instability_found_within_search / indeterminate, API и

СПЕЦИФИКАЦИЯ, НЕ реализация: runtime-код не менялся, поиск
минимумов по-прежнему НЕ реализован, статус stable не предусмотрен

Новых числовых данных НЕ импортировано: тестовые
