## 1. Назначение и происхождение

Production-реализация ln(x) и ln(1+x) с математически доказанной для каждого
вызова границей:

```
lowerBound <= ln(точный аргумент) <= upperBound,
absoluteErrorBound >= max(value - lowerBound, upperBound - value).
```

Алгоритм НЕ разрабатывался заново: ядро ПЕРЕНЕСЕНО из независимого оракула
численного аудита Stage 4.4.4.4.1-A (`Core/tpdNumericalErrorAuditOracle.ts`,
функция `tsLog` и её зависимости). Перенесены:

- double-double примитивы: Knuth/Dekker `twoSum` / `twoProduct`,
  быстрое `quickTwoSum`, DD-сложение/вычитание/умножение, QD-деление
  (три уточняющих шага частного);
- направленное округление по битам binary64: `nextUp` / `nextDown`;
- ball/enclosure-арифметика с наружу округлёнными радиусами
  (сложение, умножение, умножение на скаляр, деление с нижней границей
  знаменателя);
- точное извлечение binary64-экспоненты по битам с подъёмом 2^512 для
  субнормальных чисел (перенос `tsFloorLog2`);
- вычисление ln(2) строгим рядом 2·atanh(1/3) (68 членов, ball-деление
  1/3, кэш);
- ряд atanh для ln(m) = 2·Σ t^(2n+1)/(2n+1), t = (m-1)/(m+1), |t| <= 1/3,
  N = 44 члена, суммирование в ball-арифметике;
- `tsLog`-цепочка в целом: редукция → t-enclosure → ряд → остаток →
  восстановление ln(x) = ln(m) + k·ln(2).

НЕ переносились (вне объёма ядра): PR-кубический решатель оракула,
изоляция корней, mixture-оракул, TPD-оракул, сценарный harness.
Модуль НЕ импортирует `tpdNumericalErrorAuditOracle.ts`; оракул Stage A
не изменён.

Имена API имеют production-префикс `certified...` (задание §2).

## 2. Алгоритм

### 2.1. certifiedLn(x)

- Вход: все строго положительные конечные binary64, включая субнормальные,
  `Number.MIN_VALUE`, `Number.MAX_VALUE`. x <= 0 (включая ±0), NaN, ±Infinity —
  fail-closed (`non_positive_argument` / `invalid_input`). Ни одной
  платформенной трансцендентальной функции.
- Редукция: x — точный binary64; разложение x = m·2^k, m ∈ [1, 2),
  выполняется ТОЧНО по битам (экспонента — из битового паттерна;
  субнормальные — точным подъёмом 2^512 и битовым извлечением;
  масштабирование — точными степенями двойки `certifiedPow2`).
- Ряд: t = (m-1)/(m+1) ∈ [-1/3, 1/3); ln(m) = 2·Σ_{n=0}^{43} t^(2n+1)/(2n+1)
  в ball-арифметике.
- Восстановление: ln(x) = ln(m) + k·ln(2); ln(2) = 2·atanh(1/3), 1/3 —
  ball-деление (НЕ binary64-константа), enclosure кэшируется.
- Специальный случай: ln(1) — точный +0 (value = lowerBound =
  upperBound = absoluteErrorBound = 0).

### 2.2. certifiedLog1p(x)

Второй ряд НЕ вводится. Бинарное 1+x НЕ вычисляется (при |x| < eps
добавка x теряется напрочь): сумма 1+x строится ТОЧНО алгоритмом twoSum
как DD-пара (s, e), s + e = 1 + x безусловно точно для любых binary64,
затем точная редукция DD-значения и тот же внутренний certify-путь
`lnBallOfReduced`, что у certifiedLn.

Специальные случаи: x = +0 → точный +0; x = -0 → точный -0 (IEEE-конвенция
log1p); x <= -1, NaN, ±Infinity — fail-closed. Около -1 малая добавка
сохраняется в младшей DD-части (twoSum точен при любых величинах
слагаемых).

### 2.3. Остаток ряда — формальное обоснование

Сумма обрывается после N = 44 членов (n = 0..43): последний включённый
член имеет степень 2N-1 = 87, поэтому ПЕРВЫЙ отброшенный член имеет
степень 2N+1 = 89, и для ряда

```
ln(m) = 2·Σ_{n=0}^{N-1} t^(2n+1)/(2n+1) + R_N,  0 <= t < 1/3:
```

- знакопостоянность: все члены неотрицательны при t >= 0 (для t < 0 все
  члены НЕПОЛОЖИТЕЛЬНЫ, т.е. знаки НЕ чередуются — ряд по нечётным
  степеням t сохраняет знак t; Stage 4.4.4.4.1-D closeout: ранее было
  ошибочно указано чередование). Поэтому для любого знака t хвост
  мажорируется по модулю: |R_N| <= первому отброшенному по модулю члену,
  и геометрическая оценка ниже остаётся в силе без изменений;
- геометрическая мажоранта хвоста: |R_N| <= 2·|t|^(2N+1)/((2N+1)·(1-t^2)).

Реализация (`seriesRemainderUp`): числитель 2·tUp^(2N+1) — ровно 2N
умножений на tUp после начального 2·tUp, все округления вверх; знаменатель
(2N+1)·(1 − tUp²) — (1 − t²) вниз, умножение вниз, один nextDown; tUp =
наружная оценка фактического tMax enclosure. Неположительная нижняя
граница (1 − t²) или знаменателя — fail-closed. Эмпирический запас вместо
остатка НЕ используется; N не уменьшается.

Для |t| < 1/3: |R_N| < 2·3^-(2N+1)/(89·(8/9)) ~ 2.5e-45 — на 12 порядков
ниже двойной точности; enclosure корректен с запасом.

### 2.4. Границы результата (tight, 1 ulp)

`ballLo`/`ballHi`: DD-сумма центра с (±r), δ-поправка 2^-104·масштаб
(покрывает DD-остаток с запасом 4x; на субнормальном масштабе ddAdd точен,
δ = 0), затем ровно ОДИН направленный шаг за fl (лемма
nextDown(fl(y)) <= y для любого вещественного y, включая стыки бинад).
Зазоры `absoluteErrorBound` — точный twoSum с наружным шагом. Типичный
результат: absoluteErrorBound = 1 ulp value; lowerBound = nextDown(value),
upperBound = nextUp(value) (tight-границы переноса, §4 шапки модуля).

## 3. Отличия переноса от оракула (найдено и исправлено)

Оракул Stage A НЕ изменялся; все различия — только в новом модуле.

1. **Остаток ряда** (математическая ошибка перенесённой версии):
   оракульная `tsSeriesRemainderUp` строит границу от члена степени
   2N+3 и тем самым пропускает член t^(2N+1)/(2N+1) (~2.5e-45 для N=44);
   числово это замаскировано TS_WIDEN-запасом радиусов (~|c|·2^-100),
   поэтому enclosure Stage A остаются корректными, но документированная
   граница не покрывала фактическое усечение. В ядре формула исправлена
   (§2.3). Эмпирический этаж max(1e-12, 1-t²) оракула убран: при |t| → 1
   он занижал бы знаменатель и лишал границу строгости; здесь —
   строгий subDown и fail-closed.
2. **Точная редукция входа до шаров** (расширение контракта): оракул
   строит ball ДО редукции; его радиусный пол 2^-1074 делает
   positivity-проверку недостижимой для |x| < ~1e-323 (корректный
   fail-closed оракула, но не production-контракт). Ядро выполняет
   редукцию ТОЧНО над самим входом (биты, степени двойки, twoSum) и
   строит шары только для m ∈ [0.5, 2), где радиусные полы не разрушают
   знака. Это покрывает ВСЕ положительные конечные binary64, включая
   `Number.MIN_VALUE`.
3. **Дефект переноса `certifiedPow2`** (найден перенос-тестом; оракула
   не касается — он берёт степени двойки как обычные double-множители):
   субнормальная ветвь размещала мантиссный бит выражением `1 << i` в
   младшем 32-битном слове; JS-сдвиги берут счётчик по модулю 32, поэтому
   для i >= 32 молча строилась степень 2^((i mod 32) − 1074). Проявление:
   certifiedPow2(-1023) = 2^-1055 (ошибка в 2^32 раз), ln для верхней
   бинады [2^1023, 2^1024) ломался: ln(Number.MAX_VALUE) ~ 702.65 вместо
   709.78, радиус ~1e7. Исправлено явным размещением бита по словам
   (i < 32 → младшее слово, i >= 32 → старшее со сдвигом i − 32).
   Регрессионное покрытие: верхняя бинада и Number.MAX_VALUE —
   в тестах ядра (точки и значение 709.782712893384).
4. **Tight-границы результата** (улучшение качества, не дефект оракула):
   double-эндпоинты enclosure оптимизированы с ~2 ulp до 1 ulp (§2.4).
5. **Дефект переноса `ballLo`/`ballHi`** (найден перенос-тестом; оракула
   не касается): DD-сумма центра с (±r) ошибочно трактовалась как Ball
   (обращение к полю `.c` у значения типа Dd) — каждый вызов падал с
   TypeError, certified-функции возвращали enclosure_failure на любом
   входе. Исправлено: ddAdd возвращает Dd, magnitude/значение берутся
   напрямую (`ddMag(lowerDD)` / `ddValue(lowerDD)`).

## 4. Поддержанные входные диапазоны

- `certifiedLn`: 0 < x < +Infinity, все положительные конечные binary64
  (нормальные, субнормальные, `Number.MIN_VALUE`, `Number.MAX_VALUE`).
  Без нижней границы mole fraction / величины аргумента.
- `certifiedLog1p`: конечные binary64 x > -1. Фактические диапазоны
  production call sites (задание §4.1; основание: выбранный физический
  корень удовлетворяет Z > B > 0, поэтому 0 < B/Z < 1; TPD-ветка log1p —
  только после проверки |relativeDifference| <= 0.5):

  | Call site | Аргумент log1p | Диапазон |
  |---|---|---|
  | PR `lnZMinusB` (pure + mixture) | `-B/Z` | строго (-1, 0) |
  | PR положительный log-ratio член | `(1+sqrt(2))·B/Z` | (0, 2.415) |
  | PR отрицательный log-ratio член | `(1-sqrt(2))·B/Z` | (-0.415, 0) |
  | TPD близкие доли | `(w-z)/z` | [-0.5, 0.5] |

  Эти диапазоны покрываются контрактом целиком (x > -1) и покрыты тестами
  (включая значения по обе стороны границ). `certifiedLog1p` не отказывает
  на любом корректном x > -1; заявленный контракт шире фактических
  call sites и не требует отдельного «диапазонного» API.

- Отказы: x <= 0 для ln (`non_positive_argument`); x <= -1 для log1p
  (`at_or_below_minus_one`); NaN/±Infinity (`invalid_input`); потеря
  конечности enclosure в любом звене (`enclosure_failure`). Все отказы —
  fail-closed, без NaN в успехе.

## 5. Независимый эталон и золотые векторы

Среда генерации не имела Python (decimal недоступен), поэтому эталон
построен независимым от kernel-кода способом: BigInt fixed-point
Q = 420 бит (~126 десятичных знаков), 150 членов ряда atanh, ТОЧНАЯ
рациональная редукция входа по битам (степени двойки сокращаются точно;
1+x — точная дробь N/D). Другая точность, другое суммирование, другая
редукция — эталон не разделяет с ядром ни одной операции. Эталон
зафиксирован дважды: golden decimal-строками (110 знаков после точки,
12 векторов) и runtime-реализацией в
`Tests/certifiedLogarithm.test.ts`, проверяющей containment на полной
батарее при каждом запуске тестов.

Ограничение Q=420 (Stage 4.4.4.4.1-D): для СУБНОРМАЛЬНЫХ аргументов
log1p (например ±Number.MIN_VALUE = ±2^-1074) масштаб 2^420 ниже
представимого значения — эталон Q=420 теряет аргумент и получает ноль,
поэтому он НЕ может сертифицировать субнормальный log1p. Для них
добавлен ОТДЕЛЬНЫЙ независимый высокоточный путь (не затрагивающий
существующую батарею Q=420): ln(1+x) = 2·atanh(t), t = x/(2+x), где t
вычисляется ТОЧНОЙ рациональной арифметикой N/(2D+N) по битам binary64,
ряд 2·Σ_{n=0}^{449} t^(2n+1)/(2n+1) — BigInt interval arithmetic с
направленным округлением КАЖДОГО шага наружу (floor/ceil), Q=1200 бит,
остаток |R_450| <= 2|t|^901/(901(1-t^2)) добавляется наружу; путь не
использует production kernel, Math.log/Math.log1p и ln(2)-кэш. Reference
возвращает ИНТЕРВАЛ (не одно число); production double-границы
конвертируются в Q=1200 тоже наружу. На ±MIN_VALUE, ±3·MIN_VALUE,
малых нормальных, 1e-16 и границах ±0.5 reference interval содержится в
production enclosure (12/12); фактические границы ядра для ±MIN_VALUE —
[−7.888609052210388e-31, +7.888609052210388e-31] при value = +0.

Замеры на контрольной батарее (43 точки: ln — степени двойки и соседи,
субнормальные, MIN_VALUE/MIN_NORMAL/MAX_VALUE, верхняя бинада; log1p —
±0, субнормальные, nextUp(-1), ±0.5 и соседи, границы диапазонов,
аргументы всех трёх PR-термов на фикстуре Stage 4.4.4.3.1):
- containment эталона в [lowerBound, upperBound]: 43/43, нарушений 0;
- максимальное расхождение value с точным значением: 1.59 ulp
  (контракт — enclosure, не correctly-rounded; регрессионный порог
  теста — 4 ulp);
- максимальный absoluteErrorBound: 1 ulp value
  (1.14e-13 на ln(Number.MAX_VALUE));
- побитовое совпадение value с корректно округленным libm (V8/IEEE):
  сетка ±5000 ulp вокруг Z паровой ветви фикстуры (10001 точек, ln и
  log1p отдельно) — 0 расхождений; ln(2), ln(2^1023),
  ln(Number.MAX_VALUE) — побитово.

Побитовое совпадение с libm — ДОПОЛНИТЕЛЬНАЯ регрессионная проверка
(обеспечивает якорь `|lnPhi - libm-формы| < 1e-30` в
pengRobinsonMixture.test.ts на фикстуре), НЕ эталон и НЕ доказательство:
доказательство — строгий enclosure + независимый BigInt-эталон.

Golden-векторы (строки ≥ 110 знаков, тест сверяет с enclosure и
runtime-эталоном): ln(2), ln(3), ln(0.75), ln(MIN_VALUE),
ln(MAX_VALUE), log1p(0.5), log1p(-0.5), log1p(nextUp(-1)),
log1p(1e-16), log1p(-B/Z), log1p((1±sqrt(2))·B/Z) на фикстуре.

## 6. Производительность

Статическая стоимость одного вызова: точная редукция (O(1) битовые
операции) + 44 ball-итерации ряда (каждая: ball-деление на малое целое,
два ball-умножения, ball-сложение) + остаток + сборка результата
(~2·44 умножений с направленным округлением). ln(2) вычисляется один
раз за процесс (кэш enclosure). Замеры в среде разработки были
невоспроизводимы (таймеры песочницы заморожены), поэтому
производительность фиксируется косвенно: полный прогон батарей ядра
(43 эталонных точки + сетка 20022 certified-вызовов + 12000 вызовов
производительности) укладывается в секундный бюджет; итоговое измерение —
длительность job `verify` CI: на финальном SHA этапа (см. §8) полный
verify (TypeScript check + тесты + линт + production build) занимает
31 с против типичных ~25-30 с на предыдущих HEAD ветки; накладные
расходы certified-вызовов поглощаются бюджетом job. N = 44, радиусы
и доказательства ради скорости НЕ ослаблялись.

Влияние на production: mixture lnPhi — 4 certified-вызова на оценку
(log + log1p + два log-ratio), pure lnPhi — те же 4, TPD — 1 вызов на
компонент в log1p-ветке, 2 в fallback. Существующие тестовые наборы
(PR, mixture, TPD, Stage A 44-сценарный аудит, benchmark-дампы)
используют ограниченное количество lnPhi-оценок; CI-бюджет job verify
покрывает замену с запасом.
