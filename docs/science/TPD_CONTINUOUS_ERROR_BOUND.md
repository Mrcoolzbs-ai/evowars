## 1. Постановка

Искомая величина — граница ошибки **вычислений** (не неопределённость
EOS/BIP и не экспериментальная ошибка модели):

```
E_TPD(D) = sup_{q ∈ D} | TPD_production(q) − TPD_exact(q) |
```

где `TPD_exact(q)` — точное вещественное значение той же PR/TPD-модели
при тех же фактических binary64-значениях входов (T, P, z, w и каталожных
Tc, Pc, omega, kij), а `TPD_production(q)` — фактический результат цепочки
`pengRobinsonMixture.ts` (feed и trial состояния, обе ветви) →
`prTangentPlaneDistance.ts`. Формула evaluator:

```
TPD(w; z) = Σ_{i ∈ supp(w)} w_i [ ln(w_i/z_i) + ln phi_i(w) − ln phi_i(z) ]
```

Per-point enclosure-ы 40 audited сценариев этапа 4.4.4.4.1-A доказательством
для континуума НЕ считаются (правило задания §1): они покрывают только
конкретные входы. Метод: validated numerics — направленное округление
наружу, доказанные enclosure-ы, adaptive interval subdivision; плотные
сетки, Monte Carlo и high-precision сверки на конечной матрице доказательством
не являются.

   `multiplicityModeAvailable = false`).
3. **lnPhi смеси** (`pengRobinsonMixture.ts`, строки ~1035–1100):
   `lnZMinusB = Math.log(Z) + Math.log1p(−B/Z)`;
   `logRatio = Math.log1p((1+√2)·B/Z) − Math.log1p((1−√2)·B/Z)`;
   `lnPhi_i = (b_i/b_mix)(Z−1) − lnZMinusB − (A/(2√2·B))·(2·S_i/a_mix − b_i/b_mix)·logRatio`;

4. **TPD evaluator** (`Core/prTangentPlaneDistance.ts`):
   `ln(w/z)` — три ветки: `w === z` → ровно +0; `|(w−z)/z| ≤ 0.5` →

5. **Классификация ошибок арифметики**: операции binary64 `+ − × ÷` и

Уточнения к статусам:

- **Звено 6 (E_Z) доказуемо без модели ошибок тригонометрических веток
  решателя**: production сам проверяет невязку полинома после вычисления
  корня; прохождение проверки даёт `|P_{A_prod,B_prod}(Z)| ≤ 1e−8·coeffScale·max(1,|Z|)³`,
  откуда `|Z − ближайший корень| ≤ (невязка + возмущение P от |ΔA|,|ΔB|)/min|P′|`
  на enclosure-е ячейки; корректность привязки к выбранной ветви — из
  непересекающихся enclosure-ов и нижней границы разделения. Ветки
  `cosh/acosh/acos/cos/cbrt` влияют только на то, каким способом получен
  корень, но не на оценку: она опирается на фактически проверенную невязку.
- **Звено 9 (E_sum)**: вклад `w_i·[ln(w_i/z_i) + ΔlnPhi_i]` и его ошибка
  стремятся к нулю при `w_i → 0+` (ошибка ln-члена ~ eps·|ln(w_i/z_i)| + eps,
  умножается на w_i), поэтому предельное поведение на support faces с
  произвольно малыми положительными долями (включая субнормальные)
  доказуемо; точные нулевые доли в сумму не входят по контракту
  `supp(w)`. Минимальная положительная доля как параметр домена
  НЕ требуется.
- **Звенья 1–6, 9** реализуемы ball-арифметикой оракула Stage 4.4.4.4.1-A
  (направленное округление наружу радиусов) с сертифицированной
  бисекцией корней на ячейку; покрытие — адаптивным подразбиением
  без дыр, с явными margin-исключениями (§5, B3) и проверкой границ
  binary64.

## 5. Блокеры

### B1 — решающий, математический: нет сертифицированного контракта ошибки платформенных логарифмов в production

Production-цепочка lnPhi и log-ratio содержит `Math.log(Z)`,
`Math.log1p(−B/Z)`, `Math.log1p(±(1±√2)B/Z)`, `Math.log1p((w−z)/z)`,
`Math.log(w)`, `Math.log(z)` (файлы по §3, пп. 3–4). Точное значение
`TPD_exact` использует точный `ln` от точных вещественных аргументов;
ошибка production в этих звеньях содержит член
`|libm_log(x) − ln(x)|` для фактических double-аргументов `x(q)`.

Для sup по непрерывной области этот член неограничен без контракта на
libm: интервальное подразбиение ограничивает аргументы, но не ошибку
реализации логарифма. Для CI-runtime (V8, реализация fdlibm-класса)
**документированного сертифицированного порога ошибки не существует**;
известные неформальные утверждения («~1 ulp») — не контракт и не
доказательство для конкретной версии runtime. Собственный стандарт
проекта это уже признал дважды:

- оракул Stage 4.4.4.4.1-A построен **полностью без libm**
  («Трансцендентных функций libm/V8 нет»: собственный строгий ln через
  битовую редукцию и ряд atanh, доказательный sqrt); платформенный
  `Math.log2` был удалён из оракула как нарушение независимости;
- аудит зафиксировал фактическое отклонение V8/fdlibm `Math.log(3)` от
  correctly-rounded на 1 ulp (4.747254313187558e-16 в CI) — эмпирическое
  наблюдение, не граница.

Замена production `Math.log/Math.log1p` на доказанные реализации —
изменение production-кода, на этом этапе **запрещённое** (§7 задания).
Следовательно, `E_lnPhi(D)` и `E_logRatio(D)` недоказуемы, и конечная
доказанная `E_TPD(D)` не существует на текущем контракте. Это единственное
фундаментальное математическое звено-пробел; остальные блокеры — ограничения
области и инфраструктуры.

### B2 — давление: нерешённый параметр домена

Каталог даёт применимость BIP `co2|n2` только по температуре
[228.15, 273.15] K; давление в provenance отсутствует. Заявление источника
о пригодности PR до ~30 МПа документировано в каталоге как ОБЩАЯ
применимость модели, а НЕ покрытие измерений CO₂–N₂ (Table A4 источника —
до ~5.92 МПа, и по ней original BIP воспроизводит давление точки кипения
с отклонениями 21–35%). Верифицированного диапазона P для этого BIP не
существует, и выдавать общую применимость PR за валидацию BIP нельзя.
Любой числовой диапазон P для `D` возможен только как **явно назначенный
численный рабочий диапазон** (допустимо заданием), с фиксацией его как
назначения, а не как физической валидации. Это ограничение домена, не
математический блокер, но решение о назначении — вне пределов одного
прохода аудита, если не задано извне.

### B3 — топология/кратность: validatedDomain с необходимостью собственное подмножество с дырами

Три независимых факта:

1. **Контракт кратности.** PR-результат не содержит знака дискриминанта
   и multiplicity metadata (`multiplicityModeAvailable = false` —
   фактическое состояние контракта 4.4.4.3, §7.2 п. 4.1). Машино-проверяемый
   предикат §7.2 п. 4.3 (проверка 7) при этом **исключает** из
   `validatedDomain` все точки с `physicalRootCount = 1` или `2`:
   near-merge режим из доступных данных точки невыводим проверяемо, и
   «неизвестная кратность НЕ интерпретируется как отсутствие near-merge».
   Аудиторская re-деривация знака D оракулом на ячейках возможна для
   самой оценки ошибки, но предикат §7.2 работает от данных PR-контракта
   точки, поэтому `validatedDomain ⊆ {physicalRootCount = 3,
   well-separated}` при текущем контракте.
2. **Неизбежность 1-корневых состояний.** В полном симплексе составов
   co2/n2 при T ∈ [228.15, 273.15] K и умеренных P один действительный
   корень — норма (этап A: чистый N₂ при 250 K / 1 МПа — 1 действительный корень;
   смеси при 1–2 МПа — 1 корень). Требование задания не сужать составы
   (никакого интервала xCO2 = 0.95–0.995) означает, что TPD search по
   спецификации будет посещать состояния, которые предикат §7.2 при
   `multiplicityModeAvailable = false` не пускает в validatedDomain.
3. **Поверхности слияния и Z ≈ B внутри T-диапазона.** D = 0 (слияние
   пары корней) — поверхность внутри T ∈ [228.15, 273.15] K при P
   порядка единиц МПа (этап A: 250 K, CO₂-rich, последняя 3-корневая
   точка ≈ 3.3437 МПа); вблизи неё нет равномерного δ-разделения и
   `min|P′| → 0`, оценка E_Z через невязку вырождается — нужны
   margin-исключения. При `Z → B+` обусловленность lnPhi-членов
   ~ `eps·B/(Z−B)` неограничена — нужен margin `Z ≥ B(1+θ)` с
   обоснованием θ из доказанного покрытия, не подбор под тест.

Итог: `validatedDomain` на текущем контракте — обязательно собственное
подмножество с дырами пространства, которое может посетить TPD search.
Это разрешено заданием при явной фиксации, но означает: точки вне
`validatedDomain` остаются неклассифицированными по C1–C4, и неполное
покрытие не даёт права на `no_instability_found_within_search`.

### B4 — воспроизводимость из committed harness в CI (практический)

Сертифицированное адаптивное подразбиение домена размерности ≥ 4
(T, P, z_CO2, w_CO2; 4 комбинации ветвей feed/trial; support faces
{co2,n2}, {co2}, {n2}) с сертифицированной бисекцией корней на ячейку
и проверкой покрытия без дыр не укладывается в бюджет CI job `verify`
(~30 с). Критерий GO «результат воспроизводим из committed audit harness»
требует либо long-running среды аудита, либо иерархической верификации
committed покрытия (список ячеек + повторная проверка enclosure-ов) —
отдельного инфраструктурного решения. Блокер вторичен: бессмысленно
до B1, но самостоятельного прохождения не даёт.

## 8. Что остаётся вне validated domain (текущий контракт)

- Все состояния с `physicalRootCount = 1` или `2` — по предикату §7.2
  п. 4.3 при `multiplicityModeAvailable = false` (включая обширные
  N₂-доминированные и умеренно-барные области, которые TPD search обязан
  уметь посещать).
